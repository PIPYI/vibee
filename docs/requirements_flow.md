# 요구사항 · 의사결정 플로우 (기능 3.1)

> 루트 `README.md`의 **"1. 요구사항 / 설계 문서 공동 작성"** 기능의 동작 설계.

## 1. 범위

이 문서는 **프로젝트 시작 시점**의 기능 하나만 다룬다.

| 기능 | 시점 | 이 문서 |
| --- | --- | --- |
| 요구사항 · 의사결정 | **프로젝트 시작** | ✅ |
| Wiki / 코드베이스 학습 | 개발 도중 + 완성 후 | ✗ |
| 코드맵 시각화 · 기술부채 | 완성된 코드베이스 | ✗ |
| Drift 관리 | 완성 후 확장 시 | ✗ |

시작 시점이므로 **아직 코드가 없다.** 코드 분석·시각화와는 다루는 대상 자체가 다르다
(`ontology_schema.md`는 완성된 코드를 분석하는 역방향 문서이며, 이 플로우와 직접 연결되지 않는다).

## 2. 전제

- **사용자는 완전한 비전공자다.** 기술 용어로 묻는 질문에는 답할 수 없다.
- **사용자는 도구를 하나만 쓴다.** 귀찮아서 Codex나 Claude Code 하나를 골랐고,
  우리 앱은 거기에 **붙어 있는 형태**다.
- **우리 앱은 코딩 전 단계다.** 설계도와 harness를 만들어 넘겨주고 손을 뗀다.
  실제 코딩은 사용자의 도구 환경에서 일어난다.
- **BYOA.** 인터뷰조차 우리가 모델을 직접 부르지 않고, 사용자의 에이전트로 수행한다
  (`BYOA_MCP_INTEGRATION_SPIKE.md`에서 검증한 구조를 그대로 사용).

## 3. 전체 플로우

```text
[0] 진입
    비전공자가 빈 프로젝트 디렉토리를 열고 앱을 켠다

[1] 인터뷰                        ← 우리 앱이 사용자의 codex/claude에게 시킴
    에이전트가 먼저 질문 (최소 4개)
      ↕ 멀티턴 (질문 하나 = turn 하나)
    사용자가 답하거나, 그냥 하고 싶은 말을 함
      ↓
    누적: ACTOR / REQ / SURFACE / ENTITY / FLOW / RULE / DEC
      ↓
    초안 시점 (§4.10) — 완성이 아니라 "처음 보여줄 때"

[2] 정리
    ├─→ 사람용: 이야기로 풀어쓴 설명 + 화면 목록
    └─→ 에이전트용: app_design.md
      ↓
    초안을 놓고 대화 계속  ──────────┐
      · "이건 아닌데" → 수정          │
      · "이것도 필요해" → 추가        │  [1]과 오가며 반복
      · 경계 조건 질문 3~5개 (§4.9)   │
      ↓                              │
    사용자가 "됐다" ────────────────┘
      (부실하면 경고만 하고 보내준다)

[3] harness 생성
    AGENTS.md / CLAUDE.md

[4] 인계
    "이제 Codex를 열고 이 폴더에서 작업하세요" + 첫 프롬프트 제안
      ↓
    사용자가 자기 도구에서 코딩 (우리 앱은 관여하지 않음)
      ↓
    완성된 코드베이스가 다시 우리 앱으로 → 이후 기능들(wiki, 시각화, drift)
```

## 4. [1] 인터뷰

### 4.1 산출 단위

**"무엇을 만들고 무엇을 안 만드는가"만으로는 설계가 너무 약하다.** 기능 목록이 같아도
동작 규칙·순서·데이터 관계가 다르면 완전히 다른 서비스가 나온다. 에이전트는 그 빈칸을
전부 임의로 채운다.

목표는 인터뷰 결과만으로 **에이전트가 유스케이스·entity relation·flow·activity·state·
sequence를 전부 파악할 수 있는 것**이다. 각 다이어그램을 만들려면 무엇이 필요한지 거꾸로
따지면 단위가 정해진다.

| 다이어그램 | 필요한 것 |
| --- | --- |
| 유스케이스 | 누가(ACTOR) + 무엇을 할 수 있나(REQ) |
| entity relation | 무엇이 저장되나 + 서로의 관계 |
| activity / flow | 단계의 **순서** + 분기 조건 |
| sequence | 단계마다 누가 / 어디서 / 무엇을 / 어떤 정보에 |
| state | 무언가가 가질 수 있는 상태 + 언제 바뀌나 |

겹치는 것을 정리하면 **일곱 단위**가 된다.

```text
ACTOR    누가 쓰는가
REQ      무엇을 할 수 있는가              (= 유스케이스)
SURFACE  어디서 하는가                   (= 화면)
ENTITY   무엇이 저장되는가 + 관계 + 가질 수 있는 상태
FLOW     단계의 순서 (누가 / 어디서 / 무엇을 / 어떤 정보에)
RULE     조건 · 제약
DEC      왜 그렇게 정했는가
```

예:

```text
REQ-013  회원가입
  - 이메일 기반

FLOW-002  사진 올리기
  1. 사용자가 사진을 고른다            [사진 올리기 화면]
  2. 사진을 업로드한다                 → 사진 저장소(External)에 씀
  3. 게시물을 만든다                   → 게시물(ENTITY) 생성, 상태 = 공개
  4. 초대된 사람들에게 보인다           [홈 화면]
  ※ 2에서 실패하면 다시 시도한다        → RULE-004

DEC-008
  - MVP 단계에서는 Redis를 사용하지 않는다
  - 이유: 운영 복잡도 최소화
```

#### FLOW를 별도 단위로 두는 이유

관계(edge)로 표현하면 **순서가 흐릿해진다.** `A가 B를 발생시킨다`를 여러 개 이어 붙여도
전체 순서는 재구성해야 한다. FLOW를 **순서 있는 목록**으로 두면 sequence와 activity가
그대로 나온다.

#### 단위는 산출물의 구조이지 질문의 구조가 아니다

사용자에게 "ENTITY를 말해주세요"라고 묻지 않는다. 여전히 *"그 사람이 뭘 할 수 있어야
하죠?"*라고 묻고, **답변을 우리가 이 단위로 정리한다.** 시나리오 한 문장에서 여러 단위가
동시에 나온다.

```text
"사진을 올리면 초대된 사람 모두에게 보입니다"

  → REQ     사진 올리기
  → FLOW    고르기 → 올리기 → 보이기
  → ENTITY  사진, 게시물, 초대
  → RULE    초대된 사람만 볼 수 있다
```

#### 어디서 나오는가

| 단위 | 출처 |
| --- | --- |
| ACTOR, REQ | 대화에서 직접 |
| FLOW, ENTITY | 시나리오 문장에서 **도출** |
| SURFACE | REQ에서 **도출** (묻지 않는다 — §4.7) |
| RULE | 일부는 대화에서, 일부는 AI가 짚어 물음 |
| ENTITY의 상태 | 대부분 AI가 채움 (사용자가 잘 말하지 않는다) |
| DEC | "그건 나중에" 같은 발화 + AI가 채운 기본값 |

#### DEC가 이 기능의 차별점이다

조사해 본 Microsoft의 RPG/CoderMind는 "무엇을 만드는가"는 그래프로 담지만
**"왜 그렇게 정했는가"와 "무엇을 안 하기로 했는가"를 담지 않는다.** 설계 의도 보존은
DEC 없이는 성립하지 않는다.

DEC는 구조화된 질문보다 **자유 대화에서 더 많이 나온다.** "아 그건 나중에", "그거 말고
이렇게" 같은 발화가 곧 DEC다.

> 참고: 이 일곱 단위는 협업자의 `ontology_schema.md`(완성된 코드를 분석해 시각화하는
> 역방향 문서)와 어휘가 상당히 겹친다. 다른 문제를 풀면서 수렴한 것은 둘 다 "소프트웨어가
> 무엇인가"를 기술하기 때문으로 보인다. 다만 **FLOW(순서)와 DEC(이유)는 이쪽에만 있다.**

### 4.2 질문 하나 = turn 하나

**MCP tool 호출에는 하드 월클럭 타임아웃이 있고, progress 알림으로도 연장되지 않는다**
(Agent SDK 문서에서 확인). 따라서 `ask_user`가 사람의 답을 기다리며 블로킹하면,
사용자가 고민하는 사이 turn 전체가 죽는다. 비전공자가 "이거 뭐라고 답하지" 하며 몇 분 고민하는
것은 흔한 일이다.

그래서 **블로킹하지 않는다.**

```text
[우리 앱]                          [사용자의 codex/claude]
    │  turn 시작: "인터뷰 계속해"
    │ ──────────────────────────────▶
    │                                 get_app_context
    │                                   → 지금까지 모은 REQ/DEC 확인
    │                                 ask_user({질문, why, hints})
    │ ◀──────────────────────────────    → 즉시 반환 (질문 등록만)
    │                                 turn 종료
    │
  질문을 화면에 렌더
  사용자가 답 (몇 분이 걸리든 무관)
    │
    │  turn 시작: "사용자가 이렇게 답했어: ..."
    │ ──────────────────────────────▶   같은 세션 → 앞 대화를 기억
    ⋮
```

이 구조의 근거는 전부 spike에서 실측으로 확인된 것이다.

| 확인된 사실 | 근거 |
| --- | --- |
| 세션이 재사용되어 멀티턴 대화가 이어진다 | `SPIKE_FINDINGS.md` §9 |
| 앱 상태를 에이전트가 읽을 수 있다 (`get_app_context`) | Phase A/B acceptance |
| 에이전트가 앱에 구조화된 데이터를 push할 수 있다 (`show_result`) | Phase A/B acceptance |
| Codex/Claude 모두 동일한 turn 구조로 추상화된다 | `AgentEvent` union |

장점:

- **타임아웃 없음.** 사용자가 하루 뒤에 답해도 된다.
- **검증된 것만 사용.** 새로운 통신 방식을 도입하지 않는다.
- **provider 중립.** Codex/Claude 모두 turn 구조는 동일하다.
- **중단 가능.** 질문마다 깔끔한 체크포인트가 생긴다.

> **MCP elicitation을 쓰지 않는 이유**: MCP에는 "서버가 사용자에게 묻는" 네이티브 기능이 있지만,
> 이는 **에이전트 호스트의 UI**로 뜨며 브라우저가 아니다. 우리 bridge가 가로챌 수는 있으나
> Codex와 Claude의 동작이 서로 다르다 — Finding 1·4에서 우리를 두 번 깨뜨린 것이 정확히
> 이 채널이다. BYOA 중립성을 위해 피한다.

### 4.3 무엇을 고정하고 무엇을 열어 두는가

spike에서 두 provider에게 같은 4개 질문 예산을 주었더니 **서로 다른 것을 물었다**
(`SPIKE_FINDINGS.md` §10).

```text
Claude Q3   "사진이 점점 쌓이면 어떤 식으로 묶여 있으면 좋을까요?"   → 구조 · 앨범
Claude Q4   "새로운 친구를 데려오는 건 누가 할 수 있으면?"          → 권한

Codex  Q4   "지금 사진 공유할 때 가장 불편한 점은 무엇인가요?"       → 문제 발굴
```

둘 다 좋은 질문이지만 성격이 다르고 **재현되지 않는다.** 같은 사용자가 두 번 돌리면 다른
설계가 나오고, 어떤 정보가 빠질지 예측할 수 없다.

| | 고정 | 이유 |
| --- | --- | --- |
| 질문의 **목표** (무엇을 알아내야 하나) | **고정** | 안 하면 재현되지 않고 빠지는 정보가 생긴다 |
| 질문의 **표현** (어떻게 말할까) | 열어 둠 | 앞 답변에 맞춰 말을 바꿔야 자연스럽다 |
| **답변** 형식 | 열어 둠 | 자유 텍스트가 이 설계의 핵심이다 (§4.5) |
| **산출물** 형식 | **고정** | 구조화되지 않으면 아무 데도 쓸 수 없다 (§4.11) |

목표만 고정하고 표현은 맡긴다.

```text
초안 전 (필수)
  G1  무엇을 만드는가             → REQ의 씨앗
  G2  누가 쓰고 누가 볼 수 있나    → ACTOR + 접근 규칙
  G3  핵심 행동 2~3개             → REQ
  G4  하지 않을 것                → DEC

초안 후 (필요한 것만)
  G5  경계 조건 (§4.9)
  G6  AI가 임의로 정한 것 확인 (§4.8)
```

프롬프트에 **"G1~G4가 채워지기 전에는 초안을 내지 말 것"**을 명시하면 재현성이 생긴다.

### 4.4 `ask_user` tool

```ts
ask_user({
  question: "이 서비스는 누가 쓰나요?",
  why: "화면을 몇 종류 만들지 정하려고요",        // 비전공자 안심용
  hints: ["나 혼자 쓸 거예요", "친구들끼리만", "누구나 가입해서"],
  progress: { step: 2, total: 5 },
})
```

- **`hints`는 선택지가 아니라 예시다.** 버튼으로 고르는 것이 아니라, 백지를 마주하는 부담만
  덜어주는 역할. 입력은 항상 자유 텍스트다.
- **`why`가 필요한 이유**: 왜 묻는지 모르면 비전공자는 불안해한다.
- **`progress`가 필요한 이유**: 언제 끝나는지 모르면 지친다.

### 4.5 자유 채팅은 항상 열려 있다

```text
┌─────────────────────────────────────┐
│  에이전트: 이 서비스는 누가 쓰나요?     │
│  (화면을 몇 종류 만들지 정하려고요)     │
│  예) 나 혼자 / 친구들끼리 / 누구나      │
├─────────────────────────────────────┤
│  💬 ______________________________  │  ← 항상 열려 있음
└─────────────────────────────────────┘
```

질문에 답해도 되고, 무시하고 하고 싶은 말을 해도 된다. 어느 쪽이든 다음 turn의 입력이 된다.

자유 입력이 들어오면 에이전트는 그 내용을 REQ/DEC에 반영한 뒤, 원래 질문을 다시 할지 ·
건너뛸지 · 새 질문으로 갈지 스스로 판단한다.

이에 따른 두 가지 요구사항:

1. **진행률이 흔들리는 것을 숨기지 않는다.** 사용자가 기능을 추가하면 총 개수가 늘어난다.
   "기능이 하나 늘어서 5개 → 6개가 됐어요"처럼 보여주는 편이 낫다. 내가 말한 것이 반영됐다는
   피드백이 되기 때문이다.
2. **철회가 가능해야 한다.** 자유 대화에서는 "아까 그건 취소"가 나온다. REQ/DEC가 누적만
   되어서는 안 된다. 최소한 직전 항목 취소는 있어야 한다.

### 4.6 기술 스택은 묻지 않는다

비전공자에게 "REST와 GraphQL 중 무엇을 쓸까요"는 답할 수 없는 질문이다.
`sequence`, `entity relation` 같은 모델링 개념도 마찬가지다 — **그것들은 산출물이지 질문이 아니다.**

기술 결정은 **도출한 뒤 결과만 사람의 말로 확인**받는다.

```text
❌ "이미지 저장은 S3를 쓸까요?"

✅ "사진을 올리신다고 하셨는데, 사진은 용량이 커서 따로 보관해야 합니다.
    지금은 무료로 쓸 수 있는 곳에 두고, 사람이 많아지면 그때 옮길까요?"
```

사용자가 "알아서 해줘"라고 답해도 그것은 **DEC로 기록된다** —
"이미지 저장은 초기엔 무료 티어, 확장 시 재검토". 나중에 에이전트가 다른 선택을 하려 할 때
이것이 근거가 된다.

#### 기능도 마찬가지다 — 목적을 묻고 기능은 도출한다

"로그인 기능 넣으실 건가요?"조차 기술 쪽에 가까운 질문이다. 사용자가 원하는 것은 로그인이
아니라 **"친구들끼리만 보게 하고 싶다"**이다.

```text
❌ "로그인 기능 넣으실 건가요?"

✅ "이거 누가 볼 수 있어야 하나요?"
     "나만"        → 로그인 불필요
     "친구들끼리"   → 로그인 + 초대 필요
     "누구나"       → 로그인 + 공개 가입 필요
```

### 4.7 깊이 파고들지 않는다 — 초안이 대신 답한다

한 답변에서 하위 기능을 계속 캐물으면 끝이 없다.

```text
로그인 → 회원가입? → 이메일 인증? → 비밀번호 재설정? → 소셜 로그인?
      → 탈퇴? → 탈퇴하면 그 사람 게시물은? → 복구 기간?
```

답 하나가 질문 셋을 낳는다. 그리고 **비전공자는 이 질문들에 답할 능력이 없다** —
"탈퇴 기능 넣으실 건가요?"는 사실 "탈퇴하면 그 사람이 쓴 댓글은 어떻게 되나요?"를 묻는
것인데, 그것은 한참 뒤에 마주칠 문제다.

**대신 초안이 채워서 보여주고 사용자가 고치게 한다.**

```text
1단계   "로그인 넣으실 건가요?"  →  "네"   (여기서 멈춘다)
          ↓
2단계   초안에서 AI가 상식적으로 채운다:
        "로그인을 넣으시니 회원가입도 같이 만듭니다. 비밀번호 찾기도 넣었습니다.
         탈퇴 기능은 일단 빼뒀습니다."
          ↓
3단계   사용자: "탈퇴도 있어야 해"  →  추가
```

비전공자에게는 "탈퇴 넣으실래요?"보다 **"탈퇴는 빼뒀습니다"가 훨씬 반응하기 쉽다.**
없는 것을 떠올리는 것보다 있는 것을 고치는 편이 쉽기 때문이다.

#### SURFACE(화면)도 묻지 않고 도출한다

"화면 몇 개 필요하세요?"는 답할 수 없다. REQ에서 도출된다.

```text
REQ  사진 올리기                    →  사진 올리는 화면
REQ  친구 초대하기                  →  친구 관리 화면
REQ  사진 보기 + 좋아요 + 댓글       →  피드 화면 하나에 묶임
```

마지막 줄이 중요하다 — **어떤 기능들을 한 화면에 묶을지가 실질적인 설계 결정**이며,
AI가 정한 뒤 사용자에게 보여줘야 한다.

그리고 비전공자에게는 **기능 목록보다 화면 목록이 이해하기 쉽다.** 기능은 추상적이지만
화면은 구체적이라 머릿속에 앱을 그려볼 수 있다. 초안에 화면 목록을 넣으면
*"어 검색은 없어?"*, *"알림 화면이 있어야 하는데"* 같은 반응이 바로 나온다.

**경계**: 무슨 화면이 있고 거기서 무엇을 하는지까지가 이 단계의 일이다.
그 화면이 어떻게 생겼는지(색상·폰트·레이아웃·버튼 위치)는 에이전트 또는 이후 디자인 단계의 일이다.

```text
들어감      "사진 올리기 화면 — 사진 고르기, 설명 쓰기, 올리기 버튼"
안 들어감   색상, 폰트, 레이아웃, 버튼 위치
```

### 4.8 AI가 채운 것은 표시한다

초안에서 AI가 상당 부분을 채우게 되므로 **출처를 구분해야 한다.**

```text
REQ-004  회원가입          ← 사용자가 말함
REQ-005  비밀번호 찾기      ← AI가 채움 (미확인)
DEC-002  탈퇴 기능 제외     ← AI가 채움 (미확인)
```

전체를 검토하라고 하면 읽지 않지만, **"이 3개는 제가 임의로 정했어요, 맞나 봐주세요"는 본다.**
특히 ENTITY의 상태와 경계 조건은 거의 전부 AI가 채우게 되므로, 그것들이 한곳에 모여 있으면
훑어보기 좋다.

나중에 "왜 탈퇴 기능이 없지?"라는 질문에 답할 근거도 남는다.

### 4.9 경계 조건은 AI가 짚어 준다

사용자는 경계 조건을 먼저 말하지 않는다. 그러나 코드에서는 반드시 결정된다.

```text
"사진 올리다가 인터넷이 끊기면 어떻게 할까요?"
  예) 다시 시도 / 그냥 실패 처리 / 알아서 해줘
```

전부 물으면 지치므로 **에이전트가 판단하기 애매한 것 위주로 3~5개만** 묻고,
나머지는 기본값으로 채운 뒤 §4.8의 표시를 단다. 이 질문들은 **초안 이후**에 한다.

### 4.10 종료 조건 — "완성 시점"이 아니라 "초안 시점"

"충분히 물었는가"를 판단하려면 누군가는 설계가 충분한지 알아야 하는데, **아무도 못 한다.**

- 사용자 — 비전공자라 충분한지 모른다
- AI — 판단은 하지만 사용자가 그 판단을 검증할 수 없다
- 우리 — 그 자리에 없다

그래서 "언제 충분한가" 대신 **"언제 처음 결과물을 보여줄까"**로 바꾼다. 근거는 둘이다.

1. **되돌릴 수 있는 결정이다.** 시작 단계에서 기능 추가는 [1]로 돌아가 design에 반영한다.
   완벽한 종료 시점을 찾을 필요가 없다.
2. **비전공자는 백지보다 초안에 잘 반응한다** (§4.8).

```text
1단계  최소 질문 4개
        · 뭘 만들고 싶으세요?
        · 이거 누가 쓰나요? / 누가 볼 수 있어야 하나요?
        · 그 사람이 뭘 할 수 있어야 하죠?      ← 여기서 유스케이스가 나온다
        · 반대로, 안 했으면 하는 건요?
          ↓
2단계  초안 설계도를 보여준다        ← "인터뷰 종료"가 아니라 "초안 시점"
          ↓
3단계  초안을 놓고 대화를 계속한다
        "어 이건 아닌데" → 수정 / "이것도 필요해" → 추가
        + 경계 조건 질문 3~5개 (§4.9)
          ↓
4단계  사용자가 "됐다" → harness 생성
```

**인터뷰가 끝나는 것이 아니라 성격이 바뀐다.** 백지에서 캐내는 단계에서 초안을 보며
고치는 단계로 넘어간다.

#### 초안 시점을 앞당기는 신호

- **피로 감지** — 답이 짧아지거나 "몰라", "알아서 해줘"가 반복되면 실질적인 종료 신호다.
  이때 *"지금까지 말씀하신 걸로 일단 만들어볼까요?"*라고 제안한다. 억지로 더 캐물으면
  답변 품질만 떨어진다.
- **유스케이스 소진** — 1단계에서 나온 목록을 다 훑었을 때. 다만 "끝"이 아니라 "보여줄 때"다.

#### 부실한 채로 끝내려 하면

4단계에서 사용자가 "됐다"고 했는데 설계가 부실할 수 있다. 비전공자는 부실한 것을 모른다.

**경고만 하고 보내준다.**

```text
"회원가입 방식이 아직 정해지지 않았어요. 이대로 시작할까요?"
  [그냥 시작]  [더 정하기]
```

막지 않는 이유는 사용자가 귀찮아하는 사람이기 때문이다. 못 나가게 하면 이탈한다.
정해지지 않은 채 넘어간 것은 **DEC로 기록**되어 나중에 근거가 된다.

### 4.11 산출물은 구조화되어야 한다

spike에서 초안이 **자연어 문장**으로 나왔다 (`SPIKE_FINDINGS.md` §10).

```text
· 【화면 2 — 사진 피드(첫 화면)】 최신 사진이 위로 쌓이는 한 줄 목록...
· ⚠️【제가 정한 것 1 — 앨범 없이 한 줄 피드】...
```

사람이 읽기에는 훌륭하지만 **파싱할 수 없다.** 그러면 일곱 단위를 데이터로 뽑을 수 없고,
harness를 자동 생성할 수 없으며(DEC 목록이 문장 속에 섞여 있다), 이후 기능으로 넘길 수도 없다.

따라서 산문을 돌려주는 `show_result` 대신 **구조화된 tool**이 필요하다.

```ts
save_design({
  actors:   [{ id: "A1", name: "친구" }],
  reqs:     [{ id: "REQ-1", name: "사진 올리기", source: "user" }],
  surfaces: [{ id: "S1", name: "사진 피드", shows: ["REQ-2", "REQ-3"], source: "ai" }],
  entities: [{ id: "E1", name: "사진", relations: ["E2에 속한다"], states: ["공개"] }],
  flows:    [{ id: "F1", name: "사진 올리기", steps: [
                { actor: "A1", surface: "S1", action: "사진을 고른다" },
                { actor: "A1", action: "올린다", entity: "E1", effect: "생성" } ] }],
  rules:    [{ id: "R1", text: "초대받은 사람만 볼 수 있다", constrains: ["REQ-2"] }],
  decisions:[{ id: "DEC-1", text: "광고 없음", why: "사용자 요청", source: "user" }],
})
```

- **`source: "user" | "ai"`** 가 §4.8의 "AI가 채운 것 표시"를 그대로 담는다.
- 이 데이터 하나에서 **사람용 설명과 harness를 모두 렌더**한다 (§5, §6).
- 사람이 읽을 산문은 이 데이터에서 생성하는 것이지, 그 반대가 아니다.

## 5. [2] 정리

인터뷰 결과는 **두 가지로 렌더된다.** 읽는 대상이 다르기 때문이다.

### 사람용 — 이야기로 풀어쓴 설명

`REQ-001`, `REQ-002`를 나열하면 비전공자는 읽지 못한다. 서술형이어야 한다.

> "친구들끼리 사진을 공유하는 서비스를 만듭니다. 초대받은 사람만 들어올 수 있고,
> 올린 사진에 댓글을 달 수 있습니다. **로그인은 이메일로만 하기로 했고**,
> 카카오·구글 로그인은 나중으로 미뤘습니다."

**DEC도 자연스럽게 섞여 들어가야 한다.** 사용자가 "어? 카카오 로그인 되는 줄 알았는데"라고
반응하면 그것이 바로 지금 잡아야 할 오해다. 여기서 어긋나면 [1]로 되돌아간다.

#### 목록이 아니라 시나리오로 쓴다

이것이 설계의 깊이를 결정한다. 같은 내용도 형식에 따라 잡히는 것이 다르다.

```text
❌ 목록 — 얕다
   · 로그인
   · 게시물 작성
   · 댓글

✅ 시나리오 — 규칙 · 순서 · 관계가 문장 안에 들어간다
   "친구가 초대 링크를 받아 들어옵니다. 이메일로 가입하면 바로 사진을 볼 수 있습니다.
    사진을 올리면 초대된 사람 모두에게 보입니다. 댓글은 누구나 달 수 있고,
    자기가 쓴 댓글만 지울 수 있습니다."
```

목록은 "빠진 것"을 찾게 하지만 시나리오는 **"틀린 것"을 찾게 한다.** 비전공자에게는 후자가
훨씬 쉽다. 위 문장을 읽으면 *"어 아무나 볼 수 있으면 안 되는데"*, *"댓글은 글쓴이도 지울 수
있어야지"* 같은 반응이 바로 나온다.

#### 화면 목록도 함께 보여준다

기능은 추상적이지만 화면은 구체적이라 머릿속에 앱을 그려볼 수 있다 (§4.7).

```text
홈 화면        친구들이 올린 사진을 봅니다. 좋아요와 댓글도 여기서.
사진 올리기     사진을 고르고 설명을 씁니다.
친구 관리      초대하거나 내보냅니다.
내 정보        프로필 사진과 이름을 바꿉니다.
```

### 에이전트용 — `app_design.md`

에이전트가 코드를 쓸 때 참조할 설계도. §4.1의 일곱 단위를 담되, 에이전트가 유스케이스 ·
entity relation · flow · activity · state · sequence를 도출할 수 있는 형태여야 한다.

## 6. [3] harness

두 파일의 역할과 **로딩 방식이 다르다.**

| 파일 | 담는 것 | 로딩 |
| --- | --- | --- |
| `app_design.md` | **무엇을 만드는가** (설계) | 수동 — 읽으라고 해야 읽는다 |
| `AGENTS.md` / `CLAUDE.md` | **어떻게 작업하는가** (규율) | **자동 — 세션 시작 시 주입된다** |

이 차이가 설계를 가른다. `CLAUDE.md`는 에이전트 세션이 시작될 때 자동으로 컨텍스트에 들어가지만,
`app_design.md`는 아무도 읽으라고 하지 않으면 읽히지 않는다.

따라서 **harness가 설계로 가는 포인터 역할**을 해야 하고, 반드시 지켜야 할 제약은
**자동 로드되는 쪽**에 넣어야 매 세션 지켜진다.

### harness에는 규율만 넣는다

**프로젝트가 무엇인지는 `app_design.md`가 말한다.** harness에 기능 명세를 복사해 넣으면
두 문서가 어긋났을 때 무엇이 맞는지 알 수 없게 된다. harness는 **에이전트가 코드를 쓸 때
지켜야 할 규칙**만 담는다.

내용은 두 군데서 나온다.

**① 공통 템플릿** — 프로젝트와 무관하게 "비전공자가 주인인 프로젝트"라는 사실에서 파생된다.

| 규칙 | 왜 |
| --- | --- |
| "동작합니다" 전에 실제로 실행해서 확인 | **사용자가 검증할 수 없다** |
| 자주 커밋 | 사용자는 되돌리는 법을 모른다 |
| 기술 용어를 쓰면 한 줄 풀이 | 용어가 나오면 사용자가 판단을 포기한다 |
| 파일 임의 삭제 · 폴더 재구조화 금지 | 무엇이 사라졌는지 사용자는 모른다 |
| 새 라이브러리 추가 시 이유 설명 | 나중에 사용자가 감당하지 못한다 |

**② DEC · RULE에서 파생** — 인터뷰 결과에서 자동 생성된다.

```text
DEC-002  소셜 로그인 제외   →  "소셜 로그인을 만들지 마세요. (DEC-002)"
DEC-014  결제는 게이트웨이   →  "결제는 PaymentGateway를 통해서만 접근하세요. (DEC-014)"
```

두 번째 유형이 특히 중요하다. **코드 구조 제약을 미리 박아 두어야 나중에 Architecture Drift를
비교할 기준이 생긴다** (루트 `README.md` 3.3).

### 생성 결과의 모양

각 절의 머리에 **이유 한 줄**, 그 아래 규칙. 이유가 있으면 규칙이 더 잘 지켜지지만,
문단이 길어지면 희석된다.

```markdown
# CLAUDE.md  (요구사항 인터뷰로 자동 생성 — 직접 고치지 마세요)

## 작업 전
`app_design.md`를 먼저 읽으세요. 무엇을 만드는지 거기 있습니다.
설계에 없는 것을 만들어야 할 것 같으면 먼저 물어보세요.

## 이 프로젝트의 주인은 비전공자입니다
코드를 읽지 못하고, 무엇이 잘못됐는지 판단하지 못합니다. 그래서:

- "동작합니다"라고 말하기 전에 실제로 실행해서 확인하세요.
- 되돌릴 수 있게 자주 커밋하세요.
- 설명할 때 기술 용어를 쓰려면 한 줄 풀이를 붙이세요.

## 하지 말 것
- 사용자가 만든 파일을 임의로 삭제하지 마세요.
- 폴더 구조를 임의로 재구성하지 마세요.
- 새 라이브러리를 이유 설명 없이 추가하지 마세요.
- 소셜 로그인을 만들지 마세요. (DEC-002)
- 광고·결제 관련 코드를 넣지 마세요. (DEC-005)

## 코드 규칙
- 결제는 PaymentGateway를 통해서만 접근하세요. (DEC-014)
- 화면 컴포넌트에서 DB에 직접 접근하지 마세요.
- 주석은 한글로 쓰세요. 사용자가 나중에 읽습니다.
```

`AGENTS.md`(Codex)와 `CLAUDE.md`(Claude Code)는 **같은 소스에서 렌더**한다.

> **규칙이 많아지면 오히려 무시된다.** "하지 말 것"은 5개 이내로 제한하고, DEC이 많은
> 프로젝트라면 중요한 것만 harness에 넣고 나머지는 `app_design.md`로 미룬다.

### harness의 한계 — 명시해 둘 것

**`CLAUDE.md`는 권고이지 강제가 아니다.** 에이전트가 읽고 따르는 것이지, 어기는 것이 차단되지는
않는다. 그리고 코딩은 우리 앱 밖에서 일어나므로 **그 순간 우리는 개입할 수 없다.**

따라서 이 단계의 drift 대응은 **예방(best effort)까지다.** 어긋난 것을 실제로 잡아내는 일은
완성된 코드베이스가 우리 앱으로 돌아온 뒤, 이후 기능(3.3 drift 관리)이 담당한다.

## 7. [4] 인계

인계 시점에 프로젝트 디렉토리에 남는 것:

```text
<프로젝트>/
├── app_design.md        설계도
├── AGENTS.md            Codex용 규칙
├── CLAUDE.md            Claude Code용 규칙
└── .project-intel/      REQ/DEC 원본 (이후 기능이 사용)
```

사용자에게 보여줄 것:

- "이제 Codex를 열고 이 폴더에서 작업하세요."
- **첫 프롬프트 제안** — 비전공자는 빈 창을 마주하면 막힌다.
  예: `app_design.md를 읽고 회원가입부터 만들어줘`

### 인터뷰 세션은 어떻게 되는가

인터뷰가 사용자의 에이전트로 수행되므로, 끝난 시점에 그 프로젝트 디렉토리에 **세션이 하나
남아 있다.** `codex resume` / `claude -c`로 이어받을 수 있다(spike에서 확인).

다만 그 세션은 인터뷰 문답으로 가득 차 있으므로 **코딩은 새 세션으로 시작하는 편이 깔끔하다.**
`CLAUDE.md`가 자동 로드되므로 새 세션도 설계 의도를 안다. 인터뷰 세션은 "그때 왜 이렇게
정했는지"를 되짚는 기록으로 남는다.

> 참고: Claude Code는 SDK로 만든 세션을 `--resume` 목록에 표시하지 않는다
> (`SPIKE_FINDINGS.md` Finding 8). 세션 ID를 사용자에게 노출해야 이어받을 수 있다.

## 8. 미정 / 검증 필요

### 미정

- **3단계(초안 이후) 질문의 구성.** 1단계 최소 4개는 정했으나(§4.10), 초안을 놓고 무엇을
  어떤 순서로 되물을지는 정하지 않았다. AI가 스스로 단계를 정하는 구조도 검토 중.
- **일곱 단위의 저장 형식.** `.project-intel/` 아래 어떤 파일로 나눌지.
- **철회 처리.** 자유 대화에서 "아까 그건 취소"가 나올 때 어디까지 되돌릴지 (§4.5).
- **협업자의 `ontology_schema.md`와의 관계.** 어휘가 상당히 겹치므로(§4.1), 나중에
  인터뷰 산출물이 시각화 입력으로 이어질 수 있을지 맞춰볼 필요가 있다.

### 검증된 것 (2026-08-20)

이 플로우의 핵심 가설은 **spike로 확인했다** (`SPIKE_FINDINGS.md` §10).

> 에이전트가 구조화된 질문을 던지고 turn을 끝낸다 →
> 사용자가 답한다 →
> 다음 turn이 문맥을 이어받는다

Codex와 Claude 양쪽에서 성립했다. 함께 확인된 것:

- **블로킹하지 않는 `ask_user`가 맞다.** MCP 타임아웃을 피하면서 멀티턴이 성립한다 (§4.2).
- **최소 4개 질문으로 쓸 만한 초안이 나온다** (§4.10). 화면 6개와 그 안의 동작까지 제안했다.
- **초안이 설계한 형태로 나온다** — 화면 목록, AI가 채운 항목 표시(§4.8), 제외 목록(DEC).
- **`why`와 `hints`가 실제로 유용하게 생성된다** (§4.4). 기술 용어 없이, 왜 묻는지와
  언제 끝나는지가 담긴 질문이 나왔다.
- **엉뚱한 답변도 흡수한다** (§4.5). 질문과 어긋난 답이 들어간 turn에서 agent가 그것을
  알아채고 "답이 다른 쪽으로 와서 제가 정했습니다"라고 초안에 기록했다.

### 아직 검증하지 않은 것

- **`save_design` 스키마** (§4.11). 에이전트가 이 형식을 지키는지, 특히 **FLOW의 순서와
  ENTITY 관계**가 시나리오 문장에서 실제로 도출되는지 확인해야 한다.
- **질문 목표 고정의 효과** (§4.3). G1~G4를 프롬프트에 못 박았을 때 두 provider의 질문이
  실제로 수렴하는지.
- **철회 처리** (§4.4).
- **harness 생성** (§6). `app_design.md` / `AGENTS.md` / `CLAUDE.md`를 실제로 만드는 단계.
