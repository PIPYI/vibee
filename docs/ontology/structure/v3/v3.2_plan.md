# Ontology Structure V3.2 — 분석 런타임 신뢰성과 진행 UX

## 0. 버전 기준

이 문서의 기준선은 commit `ac10424`다. 해당 커밋의 제목은 실수로 `V2.4`라고 기록됐지만,
실제 내용과 문서 계보상 공식 버전은 **V3.1**로 취급한다.

| 버전 | Git 기준 | 의미 |
|---|---|---|
| V3.0 | `b3d439f` (`V3`) | 통합 지도와 분석 Stage 분리의 첫 구현 |
| V3.1 | `ac10424` (커밋 제목 `V2.4`) | 핵심 관계 명명, 단일 여정 캔버스, 지도 UX 정리 |
| V3.2 | 이 문서 | 분석 계약·재시도·토큰·대기 UX·언어 범위 개선 |

Git 이력을 다시 쓰지 않는다. 릴리스 노트와 이후 문서에서는 `ac10424 = V3.1` 매핑을
명시해 잘못된 커밋 제목을 교정한다.

## 1. 목표

V3.2의 목표는 **분석이 오래 걸리거나 실패할 때도 원인·비용·복구 상태를 사용자가 이해할
수 있고, 모델이 큰 Bundle을 반복 출력하지 않도록 만드는 것**이다.

핵심 질문은 다섯 가지다.

1. Web과 Bridge가 같은 프로토콜·빌드를 실행 중인가?
2. 모델은 제출 전에 정확한 IR 계약을 알고 있는가?
3. 검증 실패 시 전체 Bundle이 아니라 필요한 부분만 고치는가?
4. 긴 대기 중 현재 활동과 사용량을 정직하게 보여주는가?
5. README가 없고 여러 언어가 섞인 프로젝트도 Core 근거로 분석하는가?

V3.1의 통합 지도 UI와 IR 의미는 유지한다. V3.2는 지도를 다시 디자인하는 릴리스가 아니라,
그 지도에 도달하는 분석 파이프라인을 신뢰할 수 있게 만드는 릴리스다.

## 4. 핵심 설계 결정

### D1. 실행 호환성을 분석 전에 증명한다

`GET /api/health`에 다음 값을 추가한다.

```ts
type RuntimeCompatibility = {
  protocolVersion: string;
  buildId: string;
  serverStartedAt: string;
  capabilities: string[];
};
```

Web의 기대 `protocolVersion`과 Bridge 응답이 다르면 분석 요청을 보내지 않는다.

```text
분석 엔진이 이전 버전으로 실행 중입니다.
Bridge를 다시 시작한 뒤 재시도해 주세요.
Web build a1b2 · Bridge build 9f8e
```

`buildId`가 다르더라도 protocol이 호환되면 경고만 할 수 있지만, 이벤트/StageUsage shape가
다르면 반드시 차단한다.

### D2. 스키마의 source of truth는 하나만 둔다

MCP 도구 설명에 타입을 사람이 다시 적지 않는다. `ANALYSIS_BUNDLE_SCHEMA`에서 다음 두 산출물을
생성한다.

1. MCP가 모델에 제공하는 정확한 input schema
2. enum·필수 필드·금지 필드만 압축한 `AnalysisContractDigest`

계약에는 최소한 다음 혼동 지점을 명시한다.

- Architecture connection role: `sync | async | data | control`
- Workflow lane kind: `actor | system`
- Workflow edge role: `main | error | async | return`
- Scenario transition에는 `id`와 `label`이 없음
- `workflow.mainPath`의 모든 인접 쌍에는 실제 edge가 필요함

전체 JSON Schema를 매번 프롬프트에 복사하지 않는다. provider가 tool schema를 정확히
소비하는지 계약 테스트로 검증하고, 필요한 경우 digest를 한 번만 전달한다.

### D3. Assembly는 Core가 소유하는 draft에서 진행한다

V3.1의 `submit_analysis_bundle` 단일 제출을 다음 상태 기계로 확장한다.

```text
begin_bundle_draft
  → architecture section 제출·검증
  → workflow section 제출·검증
  → userMap section 제출·검증
  → sequence section 제출·검증
  → cross-section preflight
  → commit_bundle_draft
```

권장 계약:

```ts
type AnalysisBundleSection = "architecture" | "workflow" | "userMap" | "sequences";

type BundleDraftState = {
  draftId: string;
  taskId: string;
  baseGeneration: number;
  completedSections: AnalysisBundleSection[];
  diagnosticsBySection: Record<string, DiagnosticSummary[]>;
};
```

section 제출은 임시 draft에만 기록하고 generation을 만들지 않는다. 모든 section과 교차 참조가
검증된 뒤에만 AnalysisBundle을 원자적으로 커밋한다.

### D4. 보정은 전체 재출력이 아니라 patch다

Validator는 `path`, `currentValue`, `allowedValues`, `supportedFixes`를 구조화해 돌려준다.
모델은 실패한 section에 한정된 JSON Patch를 제출한다.

```ts
type AnalysisBundlePatch = {
  draftId: string;
  section: AnalysisBundleSection;
  operations: Array<{
    op: "add" | "remove" | "replace";
    path: string;
    value?: unknown;
  }>;
};
```

Core가 허용된 draft 경로인지, patch 후 전체 section이 유효한지 다시 검증한다. patch가
안전하지 않거나 오류가 section 전반에 걸쳐 있으면 해당 section만 다시 제출한다.

### D5. 재시도와 비용에는 실제 한도가 있다

기본 budget:

```ts
type AnalysisBudget = {
  maxValidationAttempts: 3;
  maxStageTurns: 1;
  softTokenLimit?: number;
  hardTokenLimit?: number;
};
```

- 시도 1: 최초 section 또는 cross-section 제출
- 시도 2~3: 실패한 section/patch만 자동 보정
- 시도 3도 실패: 더 이상 모델에 자동 명령을 보내지 않음
- soft limit: 현재 section 축약·Sequence 선택 축소
- hard limit: draft와 diagnostics를 보존하고 `resumable_error`로 종료

`maxAttempts`를 이벤트에 적는 것만으로는 구현 완료로 보지 않는다. 네 번째 제출이 실제로
거절되는 테스트가 있어야 한다.

### D6. 분석 Stage는 Core 상태로만 이어진다

Semantic과 Assembly는 서로 다른 provider session/turn을 사용한다. Stage 사이의 전달물은
오직 다음으로 제한한다.

- Semantic Memory digest
- Canonical Scenario 목록
- Evidence skeleton summary
- RepositoryTopology
- PreviousBundleDigest 또는 Bundle draft scaffold

수용 기준은 “reset 함수를 호출했다”가 아니라 실제 runtime에서 두 Stage의 session ID가
다르고 동시에 active인 모델 실행이 하나뿐인지로 검증한다.

서브에이전트는 V3.2 기본 경로에서 사용하지 않는다. provider가 `Task`/`Agent` 도구를 호출할
수 없도록 분석 도구 allowlist를 유지하고, 실행 요약에 `모델 실행 1개 · 서브에이전트 없음`을
표시할 수 있게 계측한다.

### D7. 진행률은 측정 가능한 상태만 말한다

모델의 내부 사고에 임의 백분율을 붙이지 않는다. 대신 Stage ledger를 둔다.

```ts
type AnalysisStageState = {
  stage: "indexing" | "semantic" | "retrieval" | "assembly" | "validation" | "commit";
  status: "pending" | "running" | "completed" | "correcting" | "failed";
  startedAt?: string;
  endedAt?: string;
  lastActivityAt?: string;
  completedUnits?: number;
  totalUnits?: number;
  message?: string;
};
```

예:

```text
의미 이해 완료 · Concept 11 · Claim 15
지도 근거 수집 완료 · anchor 7/7
지도 초안 구성 중 · 경과 8분 12초 · 마지막 활동 6초 전
검증 1/3 · 오류 119개를 3개 유형으로 묶음
사용량 · 의미 이해 30k · 지도 조립은 단계 종료 후 확정
```

provider가 token usage를 turn 종료 시에만 주면 `집계 대기` 대신 `단계 종료 후 확정`이라고
표현한다. 입력·출력·cache read·cache write 중 provider가 주지 않은 값은 `unknown`이다.

### D8. MCP 호출은 상관관계와 목적을 함께 보여준다

모든 tool call에 `toolCallId`와 호출 목적을 기록한다.

```text
관계 근거 조회 · 7/7 완료
  질문 화면에서 이어지는 관계
  API에서 이어지는 관계
  규정 매칭에서 이어지는 관계
```

`agent-stream`과 `bridge-endpoint`는 같은 `toolCallId` 아래의 관측 상태다. task의 “실제 호출
수”에는 한 번만 포함하고, 두 증거원 원본은 진단에서만 표시한다.

### D9. README는 선택 입력이고 언어 근거는 Core가 책임진다

README가 없으면 분석을 실패시키지 않는다. UI와 prompt context에 다음 provenance를 남긴다.

```text
프로젝트 설명 문서 없음
manifest · entrypoint · route · UI 문구 · 데이터 파일을 기반으로 목적을 추론합니다.
```

Python 최소 adapter는 다음을 Core origin Evidence로 만든다.

- `.py` file과 top-level class/function symbol
- FastAPI/Flask의 정적 route decorator
- 같은 프로젝트 안의 정적 import/call reference
- Pydantic/dataclass model
- `requirements.txt` 기반 runtime root

정적 분석으로 확인하지 못한 동적 사실만 agent evidence 제안으로 남긴다.

## 5. 구현 단계

### Phase 0 — 기준선과 회귀 fixture 고정

산출물:

- `ac10424 = V3.1` 버전 매핑
- README 없는 `building-law-agent-main` 진단 fixture 또는 재현 스냅샷
- V3.1 시간·토큰·도구 호출·검증 오류 baseline
- Claude와 Codex 각각의 usage/event fixture

검증:

- 동일 로그를 입력하면 실제 MCP 호출 31회와 관측 레코드 62개를 구분한다.
- 첫 제출의 119개 schema error를 유형별로 안정적으로 집계한다.

### Phase 1 — Runtime compatibility와 Stage ledger

산출물:

- protocol/build handshake
- Stage별 session/turn identity
- Stage ledger와 heartbeat
- Stage별 usage 영속화·API 복원

검증:

- 구버전 Bridge + 신버전 Web 조합에서 분석 버튼이 비활성화된다.
- Semantic/Assembly session ID가 다르다.
- 새로고침 후에도 완료된 Stage와 사용량을 `/api/state`에서 복원한다.
- provider usage가 아직 없을 때 `단계 종료 후 확정`을 표시한다.

### Phase 2 — Contract-first Assembly

산출물:

- 단일 Schema에서 생성되는 MCP 계약
- `AnalysisContractDigest`
- bundle draft 생성과 section 제출
- section shape preflight

검증:

- 잘못된 Workflow lane/edge enum은 모델 turn 전에 fixture에서 검출된다.
- Scenario transition의 `id`·`label` 추가가 첫 section 제출에서 바로 거절된다.
- 첫 전체 cross-section 검증에서 schema shape error가 0개다.

### Phase 3 — Bounded patch correction

산출물:

- section/patch 보정 API
- 진단 유형 집계와 cursor 기반 상세 조회
- 실제 retry/token budget
- 실패 draft 보존과 재개 정보

검증:

- `mainPath` edge 하나 누락 시 전체 20KB Bundle이 아니라 작은 patch만 제출한다.
- 3회 실패 후 네 번째 모델 제출이 시작되지 않는다.
- 실패 시 이전 유효 generation은 유지되고 draft는 source of truth와 분리된다.
- 최종 성공 시 `N회 자동 보정 후 완료`가 남는다.

### Phase 4 — Retrieval 절감과 Python Evidence

산출물:

- anchor 배열 batch context API
- task-local 동일 조회 캐시
- Python file/symbol/route/model/reference Evidence
- README 부재 provenance

검증:

- 7개 anchor 조회가 한 batch 요청과 7개 결과 단위로 기록된다.
- 같은 anchor·direction·hops 재조회는 Core cache를 사용한다.
- Python backend의 핵심 route와 symbol이 `origin: engine`으로 생성된다.
- README가 없어도 runtime·entrypoint·로컬 데이터 coverage gate를 통과할 수 있다.

### Phase 5 — 분석 대기 UX

산출물:

- 현재 Stage headline과 완료 Stage 요약
- 경과 시간·마지막 활동·heartbeat
- retrieval/section/validation의 측정 가능한 단위 진행
- 사용량 상태와 최종 합계
- 자동 보정·재개 가능한 실패 UI
- compact 진단과 상세 drawer

검증:

- 60초 이상 모델 tool event가 없어도 화면이 멈춘 것처럼 보이지 않는다.
- heartbeat는 진행률을 부풀리지 않고 `작업 중·마지막 활동`만 말한다.
- 119개 오류가 기본 화면에서 3~5개 유형 요약으로 표시된다.
- 최종 실패 원인이 `검증 실패`인지 `provider limit`인지 구분된다.

## 6. 테스트 전략

### 6.1 단위 테스트

- Schema → MCP contract/digest 생성 일관성
- Diagnostic grouping
- JSON Patch 경로 제한과 section 재검증
- retry/token budget 상태 전이
- toolCallId correlation
- StageUsage 합산과 unknown 처리
- Python parser의 symbol/route/reference 추출

### 6.2 통합 테스트

- Semantic → 새 Assembly session → draft → section validation → atomic commit
- 첫 section 실패 → patch → 성공
- 세 번 실패 → resumable error, 모델 추가 호출 없음
- Bridge protocol mismatch → `/api/analyze` 차단
- Web 재연결 → task/Stage/usage 복원

### 6.3 실제 프로젝트 검증

최소 세 프로젝트를 사용한다.

1. 작은 TS/JS 단일 runtime 프로젝트
2. README 없는 Next.js + Python 복합 runtime 프로젝트
3. 기존 `chungnam-mission-app-master` 재분석 프로젝트

각 프로젝트는 Claude/Codex 중 사용 가능한 provider로 3회 반복하고 median을 기록한다. 모델
변동성을 고려해 단일 실행 숫자만으로 회귀를 판단하지 않는다.

## 8. 완료 조건

다음 조건을 모두 만족하면 V3.2를 완료로 본다.

1. 실행 중인 Web과 Bridge의 protocol 불일치를 분석 전에 탐지한다.
2. Semantic/Assembly가 실제로 서로 다른 session이며 동시 모델 실행은 최대 하나다.
3. 모델이 받는 AnalysisBundle 계약과 Core Validator가 같은 schema에서 생성된다.
4. 기준 프로젝트의 첫 제출에서 schema shape error가 발생하지 않는다.
5. 검증 보정은 section/patch 단위이고 전체 Bundle을 다시 출력하지 않는다.
6. section별 세 번의 검증 제출 한도가 실제로 강제되고 초과 시 재개 가능한 실패로 종료한다.
7. 분석 화면이 현재 Stage, 완료 단위, 경과 시간, 마지막 활동을 보여준다.
8. Stage 사용량과 provider가 아직 보고하지 않은 값이 구분된다.
9. MCP 두 증거원이 한 실제 호출로 합쳐지고 배선 이상은 별도로 탐지된다.
10. README 없는 Python 복합 프로젝트의 핵심 runtime·route·symbol을 Core Evidence로 확보한다.
11. 실패해도 Semantic Memory와 이전 유효 AnalysisBundle은 손상되지 않는다.
12. V3.1 통합 지도와 사용자 여정 렌더링 회귀가 없다.

## 9. 권장 작업 순서

의존성을 고려하면 다음 순서를 바꾸지 않는 것이 좋다.

```text
Runtime handshake + Stage ledger
→ 정확한 schema contract
→ Bundle draft/section validation
→ patch correction + 실제 budget
→ batch retrieval + Python Evidence
→ 분석 대기 UX 완성
→ 실제 프로젝트 3회 benchmark
```

대기 UX를 먼저 화려하게 만드는 것은 피한다. 먼저 Runtime과 Stage 이벤트가 정확해야 UI가
정직한 정보를 표시할 수 있고, schema/patch 경로가 확정돼야 보정 진행률도 의미를 갖는다.
