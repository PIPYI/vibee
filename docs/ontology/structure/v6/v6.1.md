# Ontology Structure V6.1 — 재색인 중복·Assembly N+1·미지 언어 사각지대

## 0. 문서 상태와 기준선

- 상태: 세 항목 모두 구현 완료, 로컬 typecheck/build/test 통과. **아직 커밋되지 않았다** — 작업
  트리 변경으로만 존재한다.
- 기준 커밋: `72dd6a8` (`Guard duplicate submit_analysis_bundle and batch get_evidence lookups`)
- 대상: `prototypes/ontology/`의 재색인·Semantic·Assembly 파이프라인, evidence indexer
- 문서 역할: V6를 대체하지 않는다. V6 §3.2(Assembly N+1)·§4(index→analyze 중복 재색인)가

  사각지대 문제에 대한 별도 수정을 기록한다. §6에 V6 본문에서 갱신이 필요한 항목을 정리했다.

이 문서도 V6 §0의 용어(관찰/추론/결정/미결정)와 §7의 결과 보존 gate를 그대로 쓴다.

## 1. 배경

세 항목은 원래 "core+ai 분리 아키텍처가 archify(전량 AI 분석)보다 근본적으로 열등한가"라는 단일
질문에서 출발했다. 조사 결과 v4 §1.2–1.3이 이미 이 딜레마(순수 Core는 미지 프레임워크에서 실패,
순수 AI는 archify식 비용 폭증을 재현)를 예견하고 있었고, 실제로 관찰된 세 증상은 아키텍처 자체가
아니라 세 개의 독립된 구현 결함으로 판명됐다. 이 문서는 그 세 결함의 수정만 다룬다.

**주의**: 이 세 결함이 "archify 대비 체감 격차"의 전부라고 확정하지 않는다. 특히 V5가 QA-Maker에서
진단한 "이미 모은 evidence가 assembly 단계에서 버려짐" 문제(V5 문서, §4 참고)는 이번 수정과
별개이며 아직 손대지 않았다.

## 2. 수정 1 — index→analyze 중복 전체 재색인 (V6 §4의 미결정 질문에 대한 답)

### 관찰: 근본 원인

V6 §4는 QA Maker generation 2(`index`)→3(`index`) 사이 14초 만에 전체 discovery가 두 번 실행된
것을 관찰했지만 "먼저 index 결과 재사용 조건과 hash/dirty-file 불변식을 확인해야 한다"며 원인을
미결정으로 남겼다. 코드를 추적한 결과:

- `apps/bridge/src/index.ts`의 `performReindex`가 계산하던 `firstAnalysis`는 원래
  `before.project.semanticVersion === 0 && before.memory.concepts.length === 0`였다.
  `semanticVersion`/`memory.concepts`는 Semantic Patch가 커밋돼야 오르는데, `/api/index`
  (재색인만, 세션 없음)와 그 직후 `/api/analyze`는 둘 다 Semantic Patch가 한 번도 실행되기 전이라
  `firstAnalysis`가 **두 번째 호출에서도 여전히 true**였다.
- 이 플래그는 `packages/core/src/system-fact-lifecycle.ts`의 `buildIncrementalAnalysisPlan`에서
  `fullDiscovery`/`fullAssembly`/`semanticTurnRequired`를 모두 강제 true로 만들어, `diffEvidence`가
  정확히 계산한 "파일 변경 없음" 결과를 무시하고 매번 전체 discovery를 강제했다.
- `/api/index`(`apps/bridge/src/index.ts`의 `/api/index` 핸들러)와 `/api/analyze`(`reindex()`)는
  둘 다 독립적으로 `performReindex`를 호출하며, 서로 방금 재색인이 끝났는지 확인하는 idempotency
  체크가 없었다.

### 결정: `discoveryBaselineVersion` — Core가 직접 스탬프하는 사실

`semanticVersion`/`memory.concepts`(AI가 쓰는 상태)로 "첫 분석 여부"를 유추하는 대신,
`ProjectState`(`packages/protocol/src/index.ts:76`)에 `discoveryBaselineVersion: number`를
추가했다. 0이면 discovery가 한 번도 끝난 적이 없다는 뜻이고, `performReindex`가 커밋 시점에
한 번만 스탬프한다(`apps/bridge/src/index.ts:794-795`). `firstAnalysis`는 이제
`before.project.discoveryBaselineVersion === 0` 하나로 계산된다(`index.ts:740`).

**중요한 구분**: `reindex()`가 프롬프트 선택(`selectAnalyzePrompt`)에 쓰는 `isFirst`
(`index.ts:872`)는 **의도적으로 고치지 않았다** — "discovery가 끝났는가"와 "Vibee가 이 프로젝트의
의미를 한 번이라도 만들었는가"는 다른 질문이다. 처음에는 이 둘을 같은 필드로 통일하려 했으나,
테스트로 검증하는 과정에서 그러면 discovery만 끝나고 semantic memory는 아직 없는 **첫 실제 분석
turn**에서 Vibee가 (텅 빈 work set을 주는) incremental 프롬프트를 받게 되는 실질적 회귀를
발견해 되돌렸다. `index.ts:867-871`에 이 구분을 남겼다.

### 방어적 보강

`noRealChange` 가드(`index.ts:768-786`)를 추가했다: 파일 diff·discovery gap·fact 수명 상태 중
아무것도 안 바뀌었는데 `firstAnalysis`류 플래그의 미래 회귀로 `plan.mode`가 fast-path가 아니면
되돌리고 로그를 남긴다. 단, `before.analysisBundle !== null`(재사용할 기존 지도가 있을 때)만
발동하도록 게이트했다 — 이것도 초안에서는 이 조건이 없어서 bundle이 아직 없는 첫 분석 turn을
통째로 스킵시키는(Vibee가 한 번도 안 불려서 결과가 영원히 비는) 버그가 있었고, 테스트로 잡았다.

### 변경 파일

- `packages/protocol/src/index.ts` — `ProjectState.discoveryBaselineVersion` 필드 추가
- `packages/core/src/store.ts` — `initialProjectState`에 기본값 0 추가, `load()`에서 구
  generation의 `project.json`(이 필드가 없는)을 위한 backfill(`semanticVersion > 0`이면
  `analysisVersion`으로, 아니면 0으로)
- `apps/bridge/src/index.ts` — `firstAnalysis`/`isFirst` 재계산, 커밋 시 스탬프,
  `noRealChange` 가드
- `apps/bridge/test/v4-incremental-pipeline.test.mjs` — 회귀 테스트 추가

### 검증

- typecheck/build 전 패키지 통과
- 신규 테스트("V4 Phase 5 — /api/index 직후 /api/analyze 처럼 두 번 연속 재색인하면...")로 재현:
  같은 파일트리에 `performReindex`를 연속 호출했을 때 두 번째 호출이 `fullDiscovery: false`,
  `discoveryGaps.length: 0`임을 확인. 기존 "같은 snapshot 재분석은 fast-path" 테스트도 그대로 통과.
- 전체 스위트 통과 (§5 참고)

### 미결정 / 남은 위험

- **실제 provider E2E로 재측정하지 않았다.** V6 §4가 쓴 것과 같은 방법론(QA Maker에서
  `/api/index` → `/api/analyze` 연속 실행, `.project-intel/gen/` generation 수와 `HEAD` 타임스탬프
  비교)으로 gen2→3 중복이 실제로 사라졌는지 재확인이 필요하다. 이번 검증은 단위 테스트 수준이다.
- 구 `project.json`의 backfill 로직(`semanticVersion > 0`이면 `analysisVersion`으로 채움)은
  기존 프로젝트가 다음 재색인에서 불필요한 재작업을 한 번 더 하지 않게 하려는 것인데, 이 backfill
  자체를 실제 구 generation 데이터로 검증하지 않았다.

## 3. 수정 2 — Assembly context packet 거버넌스 (V6 §6.3의 전제가 이미 깨져 있었음)

### 관찰: §6.3이 요구한 절차가 실제로는 시행되지 않았다

V6 §6.3은 `get_assembly_context`(통합 packet)를 "model prompt를 바꾸지 않는 shadow output"으로
먼저 내보내고, coverage/parity가 누적 fixture에서 성립할 때까지 기존 개별 도구를 유지하라고
명시했다. 하지만 코드를 확인한 결과:

- `get_assembly_context`는 V6 문서를 추가한 **바로 그 커밋(`621dd1e`)**에서 이미
  `packages/mcp-server/src/index.ts`에 등록되고, Assembly 프롬프트(`apps/bridge/src/prompt.ts`)에
  "첫 자료 조회로 정확히 1회 호출"하도록 **필수 지시**로 나가 있었다.
- shadow 비교나 coverage/parity 계측 코드는 저장소 어디에도 없었다(`shadow`/`parity`/`coverage`
  검색 결과 무관한 문자열만 나옴).
- V6 문서 본문에는 `get_assembly_context`라는 이름이 **한 번도 등장하지 않는다** — 계획과 실제
  구현이 같은 커밋 안에서 이미 갈라져 있었다.

### 결정: 사전 shadow 검증은 이제 불가능하다 — 사후 롤백 레버부터

이미 프로덕션에 나가 있으므로 "shadow-first"를 지금 흉내내는 건 의미가 없다. 대신 가장 시급한
것부터 했다:

1. **롤백 레버** (`packages/protocol/src/bridge-config.ts:57,112` — `assemblyContextMode`,
   env `ONTO_ASSEMBLY_CONTEXT_PACKET`, 기본 `"on"` = 현재 동작 그대로). 기존
   `systemIntelligenceV4`(off/shadow/on)와 같은 관습을 따랐다. `"off"`일 때
   `/internal/assembly-context`(`apps/bridge/src/index.ts:1588`)가 packet 대신
   `assembly_context_disabled` 에러를 돌려주고, Assembly 프롬프트(`prompt.ts`)는
   `621dd1e` 이전의 개별 tool 흐름(+ 그 뒤 추가된 배치 tool)으로 되돌아간다
   (`index.ts:1183,1190`에서 프롬프트 빌더에 전달).
2. **구조적 안전장치** — 감사 결과와 무관하게 옳은 것들:
   - `assemblyContext()`(`apps/bridge/src/memory-api.ts`)에 `get_system_facts`와 같은
     기본 500/최대 2000 상한과 `truncated` 플래그 추가. 기존엔 무제한이었다.
   - `get_system_facts`에 `entityIds`(배열), `get_concept_context_batch`,
     `get_scenario_context_batch` 신규 tool 추가 — `get_impact_context_batch`와 같은 모양이다.
     이것이 N+1의 실질적 일반 해법이다: packet이 놓친 것(특히 Evidence 레코드 — packet은 ID만
     담고 실제 레코드는 안 담는다)도 배치로 조회할 수 있다.

**하지 않은 것**: V6 §6.3이 요구한 coverage 감사(패킷 이후 fallback 호출 빈도 계측)와 parity
스크립트(packet on/off 두 arm을 실제로 돌려 결과 diff)는 관측/측정 도구 성격이라 이번 범위에서
뺐다. 즉 **"packet이 결과를 바꾸는가"라는 §6.3의 근본 질문은 여전히 미결정이다** — 이번에 한 일은
그 질문에 답하지 않고도 문제가 발견되면 즉시 끌 수 있는 상태를 만든 것뿐이다.

### 변경 파일

- `packages/protocol/src/bridge-config.ts` — `assemblyContextMode` 필드/파서
- `apps/bridge/src/index.ts` — `/internal/assembly-context` off 분기,
  `/internal/concepts-batch`·`/internal/scenario-context-batch` 신규 엔드포인트,
  `/internal/system-facts`에 `entityIds` 필터
- `apps/bridge/src/memory-api.ts` — `assemblyContext()` 상한/truncated
- `apps/bridge/src/prompt.ts` — `buildAssemblyPrompt`/`buildIncrementalAssemblyPrompt`에
  `packetEnabled` 분기
- `packages/mcp-server/src/index.ts` — `get_concept_context_batch`/`get_scenario_context_batch`
  등록, `get_system_facts`에 `entityIds`, INSTRUCTIONS 갱신
- `apps/bridge/test/{prompt,memory-api,mcp-channel}.test.mjs` — 회귀 테스트

### 검증

- typecheck/build 전 패키지 통과
- 신규 테스트: off 모드가 `get_assembly_context`를 전혀 언급하지 않고 개별 tool 흐름(+배치
  tool)으로 되돌아가는지, `assemblyContext()`가 목록마다 독립적으로 잘리고 `truncated` 플래그를
  세우는지, MCP tool roster에 신규 tool 2개가 정확히 나타나는지
- 전체 스위트 통과 (§5 참고)

### 미결정

- packet on/off 사이의 실제 분석 결과 동등성(§6.3 원래 요구) — 미측정
- `get_assembly_context`가 이미 얼마나 fallback 호출을 유발하고 있는지 — 미계측 (구현하지 않은
  coverage 감사가 필요)

## 4. 수정 3 — 미지 언어 catch-all (V4/V5에서 제기됐지만 V6는 다루지 않은 문제)

### 관찰: 닫힌 허용목록이 만드는 완전한 사각지대

`packages/evidence/src/lang.ts`의 `isSourceFile()`은 TS/JS 계열 + Python + 4개 언어(java/csharp/
ruby/go)로 닫힌 허용목록이다. 이 목록 밖 확장자(Rust/Elixir/PHP/Kotlin/Swift 등)는
`indexProject`(`packages/evidence/src/indexer.ts`)에서 `kind:"file"` evidence조차 생성되지
않는다 — evidence graph 전체에서 존재 자체가 사라진다. `planDiscoveryGaps`
(`packages/core/src/discovery.ts`)의 기존 4가지 gap 종류는 모두 "부분적으로라도 인식된 신호"가
있어야 gap이 되므로, 완전히 미인식된 파일은 gap 목록에도 뜨지 않았다. 그런데 Assembly/Semantic
프롬프트(`apps/bridge/src/prompt.ts`)는 "gap과 영향 ID 밖은 조사하지 마라"는 하드 지시를 내리므로,
이 사각지대는 Vibee의 조사 범위 밖으로 구조적으로 봉인돼 있었다.

### 결정: 허용목록 대신 차단목록 — 특정 언어를 하드코딩하지 않는다

`packages/evidence/src/lang.ts`에 `isNeverSource()`/`collectAllRepositoryFiles()`를 추가했다.
방향을 뒤집었다: "인식된 언어만 코드로 본다" 대신 "정말로 코드가 아니라고 확신할 수 있는 것"(이미지·
폰트·미디어·압축·바이너리 산출물·잠금 파일)만 차단목록에 올리고, 나머지는 전부 "코드일 수 있다"고
본다. 새 언어가 추가돼도 이 목록에 코드 변경이 필요 없다.

- `EvidenceIndex.unindexedFiles`(`packages/protocol/src/index.ts:483`) — 허용목록 밖이라
  evidence가 안 생긴 파일들을 확장자와 함께 관측 가능하게 노출
- `indexProject`(`packages/evidence/src/indexer.ts:117-126,577`)에서
  `allPaths`(허용목록 결과)와 `collectAllRepositoryFiles()`(차단목록 결과)의 차집합으로 계산
- `planDiscoveryGaps`(`packages/core/src/discovery.ts:320-352`)가 `unindexedFiles`를 확장자별로
  묶어, 개수(≥3) 또는 전체 파일 대비 비율(≥5%) 중 하나를 넘으면 `unrecognized-source-language`
  gap(신규 `DiscoveryGapKind`, `packages/protocol/src/index.ts`)을 하나씩 만든다. 이 gap은
  `validateAnalysisBundle`을 막는 hard gate가 아니라 `get_incremental_analysis_context`에 노출되는
  investigatable gap이다 — 기존 검증 게이트는 그대로 둔다.

### 발견하고 고친 회귀: CSS/HTML/Markdown 오탐

첫 구현에서는 차단목록이 이미지·폰트·미디어·압축·바이너리만 다뤄서, `.css`(그리고 `.html`/`.md`
등)가 "미지 언어"로 분류돼 기존 CSS-only 변경 fast-path 테스트("구조와 무관한 CSS 변경도 provider
turn을 만들지 않는다")가 깨졌다. 어떤 프런트엔드 프로젝트든 CSS 파일 수가 임계치를 쉽게 넘기기
때문에 이 상태로는 거의 모든 프로젝트에서 오탐이 났을 것이다. 마크업/스타일/문서 포맷(CSS/SCSS/
SASS/LESS/HTML/Markdown/텍스트)을 차단목록에 추가해 고쳤다 — 이건 특정 "프레임워크"가 아니라
프로그래밍 언어가 아닌 것으로 이미 잘 알려진 웹/문서 포맷 범주 전체를 배제한 것이다.

### 검증

- 이 코드베이스에 지금까지 지원이 전혀 없는 언어(Elixir/Phoenix)로 새 fixture
  (`fixtures/v5/unrecognized-elixir/`)를 추가해 4개 테스트
  (`packages/core/test/unrecognized-source-language.test.mjs`) 작성:
  - 수정 전 상태 확인: `indexProject`가 이 fixture에서 evidence를 전혀 안 만든다
  - `unindexedFiles`가 확장자별로(`.ex` 3개, `.exs` 1개) 관측된다
  - `planDiscoveryGaps`가 Elixir 전용 코드 없이 `unrecognized-source-language` gap을 만들고,
    reason 텍스트가 프레임워크 이름을 언급하지 않는다 (`grep -rln "elixir|phoenix"`로 src에
    전용 코드가 없음을 별도 확인)
  - 임계치 미만(대형 저장소에서 우연히 섞인 파일 1개, 합성 입력)은 gap이 안 된다
- 기존 `route-surface-coverage.test.mjs`(Java Spring 등) 전부 통과 — 검증 게이트를 건드리지
  않았다는 확인
- `npm run eval`(fixture-app, TS/Python) 기준 회귀 없음은 **전체 test suite 통과로 간접
  확인했을 뿐, eval.mjs 자체는 실행하지 않았다** (§5 참고)

### 미결정

- 임계치(개수 ≥3, 비율 ≥5%)가 실제 프로덕션 규모 저장소에서 적절한지 실측하지 않았다. 작은
  값이라 노이즈(우연히 섞인 파일 1~2개)에 둔감하게, 큰 값이 아니라 정말 낮게 잡았다는 것 외에는
  근거가 실측이 아니라 설계 의도뿐이다.
- V5가 진단한 "assembly 단계에서 evidence가 버려짐" 문제와는 원인이 다르다 — 이 수정으로 그
  문제가 풀렸다고 주장하지 않는다.
- 새로 생긴 gap이 실제 Vibee 조사 범위/토큰 비용에 미치는 영향은 provider E2E로 측정하지 않았다.

## 5. 검증 gate 대조 (V6 §7 재사용)

| V6 §7 공통 gate | 이번 세 수정에 대해 |
| --- | --- |
| 1. 변경 전/후 같은 fixture·generation·provider로 비교 | **미실행.** provider E2E를 하지 않았다 |

비용과 자격 증명이 필요해 이 세션에서 실행하지 않았다.

## 6. V6 본문에서 갱신이 필요한 항목

이 문서는 V6를 고쳐쓰지 않지만, V6 §3.2/§4/§6.3/§7을 읽는 사람은 아래를 함께 봐야 한다.

- **V6 §3.2 (Assembly N+1)**: "미결정: 기존 69회 조회의 정보 합집합·순서·모델의 선택 경로가
  결과에 영향을 주는지 아직 검증하지 않았다"는 여전히 미결정이다. 다만 원인으로 지목된 packet
  자체는 이미 §6.3의 활성화 조건 없이 배포돼 있었다는 사실이 이번에 확인됐다(§3 참고) — V6의
  "즉시 개별 도구를 제거하거나 고정 packet만 주는 변경은 금지한다"는 문장은 **과거형으로 다시
  써야 한다.**
- **V6 §4 (index generation 2→3 중복)**: "V6은 이것을 불필요하다고 아직 결론 내리지 않는다"는
  문장은 이제 근본 원인(§2 참고)이 밝혀졌으므로 갱신 대상이다. 다만 실제 provider 실행으로
  재확인하기 전까지는 "고쳤다"고 확정하지 않는 게 이 문서의 입장이다.
- **V6 §6.3 (Assembly packet shadow-only)**: 계획과 실제 배포 사이의 괴리(§3 참고)는 V6 §6.3
  섹션 자체에 "이 계획은 실제로 시행되지 않았다"는 주석이 필요하다.
- **V6 §7 "아직 답하지 못한 질문"**: "generation 2의 index 결과를 generation 3에서 안전하게
  재사용할 수 있는 정확한 freshness 조건은 무엇인가?"에 대해 §2가 코드 레벨 답을 준다
  (`discoveryBaselineVersion`). "Assembly packet이 기존 개별 조회의 합집합과 실제 최종 bundle
  참조를 모두 덮는가?"는 여전히 미결정이다.

## 7. 이 시점에서 아직 답하지 못한 질문

- gen2→3 중복 재색인이 실제 provider 실행에서도 사라지는가 (V6 §4와 같은 방법론으로 재측정 필요)

- 이 세 수정 이후에도 V5가 진단한 "assembly 단계 evidence 폐기" 문제가 남아있는가 — 별도 조사 필요
