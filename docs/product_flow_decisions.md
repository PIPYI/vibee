## 다음 대화를 이어갈 에이전트에게

이 문서는 단순 아이디어 메모가 아니라 **제품 플로우 논의를 이어가기 위한 인수인계 문서**다. 다음 에이전트는 먼저 이 문서 전체를 읽고 아래 원칙을 지킨다.

1. 아래에서 `확정`이라고 적은 내용을 다시 선택지로 되묻지 않는다.
2. 루트 `README.md`나 기존 설계 문서가 이 문서와 충돌하면, 기존 문구를 근거로 사용자의 결정을 되돌리지 않는다.
3. 기능들이 같은 프로젝트 디렉터리를 쓴다는 이유로 하나의 상태·세션·갱신 주기를 공유한다고 가정하지 않는다.
4. 아직 정하지 않은 지점은 한 번에 하나씩, 사용자 관점의 실제 동작으로 질문한다.
5. 시각화의 세부 표현보다 먼저 **비시각 기능들의 입력, 실행 시점, 결과 수명과 상호 격리**를 정한다.
6. 현재 spike의 화면과 코드는 검증 장치다. 제품 요구사항을 spike의 현재 구현에 맞춰 축소하지 않는다.

## 이 논의를 시작한 배경

사용자는 현재 프로토타입을 최종 앱으로 보지 않는다. 프로토타입은 Codex/Claude Code 연결, MCP 왕복, 인터뷰, Drift, Wiki 같은 메커니즘을 실제 에이전트로 검증하기 위한 것이다. 검증 결과는 활용하되, 사용자 입장에서 기능 경계와 상태 관리가 혼재되어 있어 **제품 앱은 새로 만드는 방향**을 전제로 한다.

논의의 출발점은 다음 우려였다.

> README에 적힌 기능들은 서로 다른 기능인데, 하나를 사용했을 때 다른 기능이나 프로젝트 데이터가 초기화되면 문제가 된다.

그 뒤 각 기능의 기준 시점과 입력을 하나씩 분리했다. 이 과정에서 기존 문서를 하나의 통합된 제품 플로우로 해석하는 오류가 여러 번 있었고, 사용자가 다음과 같이 바로잡았다.

- “다 별개의 기능이야.”
- “인터뷰는 사용자가 새로운 프로젝트를 시작하고 싶을 때 설계도를 만드는 기능이고, 설계도와 하네스를 만들고 나면 그걸로 그 기능은 끝.”
- “완전히 다른 앱을 만들고 싶다면 새 프로젝트를 생성하거나 다른 폴더를 선택하는 것.”
- “위키·코드 분석·아키텍처/기술부채 기능은 이미 있는 코드베이스를 연결했을 때가 기준.”
- Drift는 현재 프로젝트 전체 상태를 매번 다시 판단하는 것이 아니라 “커밋 기준”.
- 인계 이후 설계와 구현을 바꾸는 것은 “연결되어 있는 Codex나 Claude Code 앱의 역할”.
- Wiki는 “다 끝나고 채팅 분석해서 학습 목적”이며 커밋으로 코드가 바뀌는 것과 무관하다.
- 코드 분석·시각화는 필요할 때 새로 실행하면 된다.
- “다 끝난 상태”는 작은 작업 하나가 아니라 end-to-end로 하나의 결과물이 모두 만들어진 상태다.
- 우리 앱에는 프로젝트 디렉터리를 입력하는 칸이 있고, 앱과 에이전트는 같은 워크스페이스를 공유한다.
- 후속 기능을 실행하면 우리 앱에 연결된 에이전트가 그 기능에 필요한 코드를 읽는다. 기능에 따라 프로젝트 코드 전체가 필요할 수도 있고 세션의 채팅 기록이 필요할 수도 있다.

위 문장들이 이후 플로우 설계의 기준이다.

## 핵심 전제

- 루트 `README.md`에 적힌 기능들은 하나의 연속된 작업 단계가 아니라 **서로 다른 목적을 가진 별개 기능**이다.
- 프로젝트의 기본 단위는 사용자가 앱에 입력한 **프로젝트 디렉터리**다.
- 우리 앱과 연결된 Codex 또는 Claude Code는 같은 디렉터리를 워크스페이스로 사용한다.
- 같은 워크스페이스를 사용하더라도 기능별 입력, 실행 시점, 세션과 결과 수명은 서로 다를 수 있다.
- 한 기능을 실행했다고 다른 기능의 상태나 산출물을 초기화하거나 삭제하면 안 된다.
- 현재 프로토타입은 아키텍처와 구현 가능성을 검증한 spike다. 제품은 새로 만들고, 검증된 메커니즘만 가져간다.

### “별개 기능”의 정확한 뜻

별개 기능이라는 말은 기능끼리 어떤 데이터도 참고하지 못한다는 뜻이 아니다. 같은 프로젝트를 설명하므로 필요한 경우 설계도, 코드, 대화, Git 이력을 읽을 수 있다. 다만 다음은 분리한다.

- **사용 목적**: 설계, 학습, 코드 이해, Drift 검토, 구조/부채 파악은 서로 다른 사용자 목표다.
- **시작 조건**: 새 프로젝트에서만 쓰는 기능과 코드가 이미 있어야 쓰는 기능이 다르다.
- **주 입력**: 인터뷰 대화, 코딩 대화, 전체 코드, 커밋 diff 등 기능마다 다르다.
- **실행 주체와 권한**: 어떤 turn은 대화 전용이고, 어떤 turn은 코드 전체 읽기가 필요하다.
- **결과 수명**: 커밋마다 이어지는 결과와 사용자가 요청할 때 새로 만드는 결과가 다르다.
- **실패 및 초기화 범위**: 한 기능의 재실행·초기화·실패가 다른 기능의 데이터를 지우면 안 된다.

데이터 참조 가능성과 기능 수명주기 공유를 혼동하지 않는 것이 중요하다.

## 프로젝트 진입 경로

현재까지 두 가지 진입 경로가 확인됐다.

### 새 앱을 만드는 경우

```text
새 프로젝트 디렉터리 지정
→ 인터뷰
→ 설계도와 harness 인계
→ 같은 디렉터리에서 연결된 에이전트가 최초 결과물 전체 구현
→ 결과물이 end-to-end로 동작
→ 후속 기능을 필요에 따라 개별 실행
```

### 이미 코드가 있는 프로젝트를 여는 경우

```text
기존 프로젝트 디렉터리 지정
→ 인터뷰를 거치지 않음
→ 코드 분석·시각화 / 아키텍처·기술부채 등 필요한 기능 실행
→ 해당 기능이 요구하는 범위의 코드·기록을 연결된 에이전트가 읽음
```

기존 코드베이스 진입에서 Wiki가 동작하려면 분석할 수 있는 Codex/Claude Code 대화 기록이 실제로 있어야 한다. Drift는 DEC/RULE 같은 프로젝트 고유 기준이 없는 기존 저장소에서 무엇을 기준으로 할지 아직 정하지 않았다.

## 전체 사용자 흐름

```text
프로젝트 디렉터리 지정
        ↓
새 프로젝트라면 요구사항 인터뷰
        ↓
설계도 + 선택한 에이전트용 harness 생성
        ↓
같은 워크스페이스에서 Codex/Claude Code가 전체 앱 구현
        ↓
하나의 동작하는 결과물이 end-to-end로 완성됨
        ↓
사용자가 우리 앱에서 필요한 후속 기능을 개별 실행
        ↓
연결된 에이전트가 기능에 필요한 코드·대화·기록을 읽고 결과 생성
```

완성된 프로젝트를 우리 앱으로 다시 가져오거나 별도로 import하는 단계는 없다. 워크스페이스가 이미 공유되어 있으므로 사용자가 기능을 실행하면 그 시점에 연결된 에이전트가 필요한 자료를 읽는다.

### “다시 우리 앱으로 돌아온다”의 의미

기존 문서에는 “완성된 코드베이스가 다시 우리 앱으로 돌아온다”는 표현이 있다. 이것은 파일을 복사하거나 저장소를 재등록한다는 뜻으로 해석하면 안 된다.

- 프로젝트 경로는 이미 앱에 연결되어 있다.
- Codex/Claude Code와 우리 앱은 같은 디렉터리를 본다.
- 사용자는 구현이 끝난 뒤 우리 앱에서 원하는 기능을 누른다.
- 그 기능을 위해 시작된 agent turn이 현재 워크스페이스를 읽는다.
- 따라서 별도 import, re-link, 결과물 업로드 과정은 없다.

우리 앱이 외부 에이전트의 “완료”를 자동 감지해야 한다는 결정도 아직 없다. 현재 합의에서 중요한 것은 완료 이후 기능을 사용한다는 사용자 흐름이지, 자동 상태 판정이 아니다.

## 기능별 역할과 수명

### 요구사항 인터뷰

- 사용자가 **새로운 프로젝트를 시작할 때** 사용한다.
- 대화를 통해 설계도와 에이전트 harness를 만든다.
- 산출물을 인계하면 인터뷰 기능의 역할은 끝난다.
- 인계 후 인터뷰를 재개하여 설계를 수정하는 제품 경로는 두지 않는다.
- 이후 설계 변경과 실제 구현은 연결된 Codex 또는 Claude Code 앱의 역할이다.
- 완전히 다른 앱을 만들려면 새 프로젝트를 만들거나 다른 폴더를 선택한다.

#### 인터뷰가 읽고 쓰는 것

- 입력은 사용자가 만들고 싶은 앱에 대한 대화다.
- 시작 시점에는 코드가 없다는 전제다.
- 대화에서 ACTOR, REQ, SURFACE, ENTITY, FLOW, RULE, DEC 같은 설계 정보를 구조화할 수 있다.
- 출력은 사람용 설계 설명, `app_design.md`, 선택한 에이전트용 `AGENTS.md` 또는 `CLAUDE.md`, 이후 참조 가능한 구조화 원본이다.
- 인터뷰 turn은 소스 코드를 구현하거나 기존 프로젝트 문서를 무차별적으로 읽는 작업 turn이 아니다.

#### 인터뷰 종료 후

- 우리 앱 안에서 인터뷰 세션을 다시 열어 설계를 고치는 경로를 제품 플로우로 두지 않는다.
- 기존 설계 변경, 기능 확장, 코드 수정은 연결된 Codex/Claude Code 앱에서 사용자가 요청한다.
- 따라서 인터뷰의 대화 상태를 영구 복원해야 한다는 기존 spike의 미정 항목은 현재 제품 플로우의 우선 요구가 아니다.
- 단, 설계 원본을 Drift 기준이나 에이전트 컨텍스트로 보존하는 문제는 별개다. 인터뷰 UI를 재개하지 않는다고 DEC/RULE 원본까지 삭제하는 것은 아니다.

### 최초 end-to-end 구현

- 인계받은 에이전트는 설계의 일부 기능만 만드는 것이 아니라 **전체 결과물을 끝까지 구현**한다.
- 여기서 “완료”는 한 번의 작은 작업이나 커밋이 끝났다는 뜻이 아니다.
- 사용자가 처음 의도한 앱이 실제로 실행되는 하나의 결과물로 모두 만들어진 상태를 뜻한다.
- 이 완료 시점 이후에 프로젝트 확장과 학습 기능을 사용한다.

#### 앱과 코딩 에이전트의 역할 경계

- 실제 소스 코드 구현의 반복 루프는 Codex/Claude Code 앱에 있다.
- 우리 앱은 설계 산출물을 넘기고, 나중에 분석·학습·검토 기능을 실행한다.
- spike의 `mode: "task"`는 Browser → Agent 제어 채널이 실제 파일을 수정할 수 있는지 확인한 acceptance 장치다. 이를 제품의 내장 코딩 화면으로 확장하지 않는다.
- 우리 앱에서 Drift를 보고 수정이 필요하다고 판단하더라도 실제 수정은 연결된 코딩 에이전트가 맡는 방향이다. 우리 앱은 필요한 프롬프트와 컨텍스트를 넘길 수 있다.

### Wiki

- 최초 결과물이 완성된 뒤, 구현 과정에서 에이전트와 나눈 **채팅 기록을 분석하는 학습 기능**이다.
- 비전공자가 대화 중 접한 낯선 말을 “이 프로젝트에서는 무엇을 뜻하는지” 이해하게 한다.
- 필요하면 설명의 근거를 찾기 위해 현재 프로젝트 코드를 읽을 수 있다.
- 가치판단, 개선 권고, 위험 평가를 하지 않는다.
- 새 커밋이 생겼다는 이유로 위키를 초기화하거나 자동 갱신하지 않는다.
- Wiki의 입력은 커밋 이력이 아니라 학습 대상이 되는 에이전트 세션의 대화와 프로젝트 맥락이다.

#### Wiki 실행 해석

```text
최초 결과물 전체 완성
→ 사용자가 Wiki 기능 실행
→ 분석 대상 코딩 세션의 채팅 기록 읽기
→ 비전공자가 모를 만한 용어 후보를 agent가 판단
→ 사용자가 학습할 항목을 선택
→ 필요하면 agent가 프로젝트 코드에서 실제 사용 위치 확인
→ 이 프로젝트 기준의 설명 생성
```

- 단순 단어 빈도 추출은 검증에서 실패했다. 낯선 용어 후보 선정은 agent 판단이 필요하다.
- 코드는 용어가 이 프로젝트에서 실제로 무엇을 뜻하는지 근거를 대기 위해 읽는다.
- 일반적인 사전 설명만 만들지 않는다.
- “위험하다”, “바꿔야 한다”, “권장한다” 같은 평가는 배제한다.
- Wiki 결과를 Markdown과 구조화 원본으로 저장할 수 있다는 메커니즘은 검증됐지만, 최종 제품의 저장 위치와 수명은 아직 확정하지 않았다.
- 어느 코딩 세션을 대상으로 할지, 여러 세션을 합칠지, 확장 작업 후 새 Wiki 분석을 어떻게 시작할지는 아직 정하지 않았다.

**확정 (2026-08-24, 아래 "후속 결정" 절에 질문·답변 전문이 있다) — 세션 범위는 사용자가 고르지 않는다.** 앱이 이 프로젝트
디렉터리의 최근 세션을 자동으로 모은다(spike 구현: 최근 순 최대 10개, 우리 앱이 시작한
대화든 사용자가 옆 창에서 CLI로 직접 한 대화든 함께). 여러 세션을 합칠지 고르게 할지를
사용자에게 묻는 UI는 두지 않는다.

**그리고 provider를 넘나들며 합치지 않는다.** "혹시 사용자가 Codex로 만들고 Claude로
Wiki를 누르면?"이라는 우려로 두 provider의 세션을 합치는 것도 검토했지만, 기각했다 —
**비전공자는 도구를 하나만 구독해서 쓴다**는 이 프로젝트의 기존 전제(`docs/requirements_flow.md`
§2 "사용자는 도구를 하나만 쓴다")와 맞지 않는 상상의 문제였다. Codex 사용자는 Codex
세션만, Claude 사용자는 Claude 세션만 본다 — 이미 그렇게 구현돼 있고 추가 작업은 없다.

### 코드 분석·시각화

- 이미 코드가 존재하는 완성된 코드베이스를 대상으로 한다.
- 사용자가 기능을 실행한 시점에 연결된 에이전트가 **프로젝트 코드 전체를 새로 읽고 분석**한다.
- 코드가 바뀌었다면 다음 실행에서 현재 코드를 다시 분석하면 된다.
- Wiki나 Drift의 상태를 입력으로 전제하거나, 이 기능 때문에 다른 결과를 초기화하지 않는다.

#### “코드 전체를 읽는다”의 의미

- 분석 범위는 일부 diff나 임의로 고른 파일이 아니라 프로젝트 전체다.
- 큰 저장소에서 agent가 한 prompt에 모든 원문을 넣어야 한다는 뜻은 아니다. 파일 탐색, 정적 분석 결과, Implementation Graph, 필요한 추가 조회 등으로 나누어 읽을 수 있다.
- 구현 최적화 때문에 사용자에게 알리지 않고 일부 폴더만 분석한 뒤 전체 프로젝트 결과인 것처럼 보여주면 안 된다.
- 이전 분석 결과를 증분 갱신하는 엔진을 내부 최적화로 쓸 수는 있지만, 사용자 플로우의 기준은 “기능을 실행한 현재 시점의 전체 프로젝트를 분석한 결과”다.
- 시각화의 Semantic Project Graph, Implementation Grounding, Framework Adapter 등 상세 설계는 `ontology/` 문서에 있다. 현재 대화에서는 시각 표현 자체보다 다른 기능과의 수명주기 분리가 우선이다.

### 설계 의도 ↔ 코드 Drift

- 인터뷰에서 저장한 DEC/RULE을 기준으로 이후 코드 변경을 검토한다.
- 검토 단위는 현재 코드베이스 전체 상태가 아니라 **개별 커밋과 그 커밋의 diff**다.
- 코드를 고치거나 확장하는 일은 연결된 Codex/Claude Code에서 수행한다.
- 커밋 변화에 따라 순차적으로 상태를 이어가는 기능은 현재로서는 Drift뿐이다.

#### 프로토타입에서 검증된 커밋 리뷰 메커니즘

다음은 현재 spike가 실제로 검증한 동작이며, 최종 UX는 별도로 정할 수 있다.

- 한 리뷰에서 여러 커밋을 처리하더라도 각 커밋은 **그 커밋 자신의 diff만으로** 판정한다.
- 이전에 본 커밋은 다시 판정하지 않도록 마지막 SHA를 저장한다.
- 위반 커밋과 무해 커밋을 함께 넣어 범용 코드 리뷰가 아니라 DEC/RULE 위반만 찾는지 검증했다.
- 코드를 고치면 새 커밋이 다음 검토 대상이 된다.
- 결정을 바꾸면 그 이후 커밋부터 새 기준을 적용한다는 메커니즘이 문서화돼 있다.

주의할 점:

- Drift는 버그, 스타일, 일반적인 베스트 프랙티스를 리뷰하는 기능이 아니다.
- 코드 분석·시각화가 전체 코드 스냅샷을 읽는 것과 Drift가 커밋 diff를 읽는 것은 서로 다른 입력 방식이다.
- 기존 코드베이스에 인터뷰 산출물이나 DEC/RULE이 없을 때 Drift를 제공할지, 제공한다면 기준을 어떻게 만들지는 미정이다.

### 아키텍처·기술부채

- 이미 코드가 존재하는 코드베이스를 연결했을 때 사용하는 별도 기능이다.
- 코드 구조와 필요한 프로젝트 기록을 어떤 범위로 읽을지, 결과를 일회성 분석으로 볼지 누적 이력으로 관리할지는 아직 확정하지 않았다.

현재 문서에는 의존성 증가, 결합도·응집도, 순환 의존성, 레이어 위반, 오래 남은 TODO, 과거 결정과의 비교가 후보로 적혀 있다. 그러나 이를 하나의 리포트로 묶을지, 사용자에게 어떤 질문에 답해주는 기능으로 만들지, Drift와 어디까지 분리할지는 다음 논의가 필요하다.

**확정 (2026-08-24, 후속 대화) — 범위를 세 가지 구체적 증상으로 좁혔다.** 사용자가 실제로
겪은 사례를 근거로 "의존성 증가·결합도·응집도·순환 의존성·레이어 위반" 같은 범용
정적분석 후보는 **범위 밖으로 뺐다** — 이건 옆 agent에게 물으면 이미 잘 답하는 범용
베스트프랙티스라서, Drift가 "버그·스타일 리뷰는 우리 몫이 아니다"라고 정한 것과 같은
이유로 이 제품이 만들 이유가 약하다. 대신 아래 셋만 다룬다. 질문·답변 전문은 아래
"후속 결정" 절의 질문 5에 있다.

1. **파일/모듈 비대화** — 설계(인터뷰의 ENTITY/REQ)가 나눠 둔 개념적 경계를 코드의 실제
   파일 구조가 아직 따르고 있는가.
2. **의미가 같은 로직의 중복** — 텍스트가 복붙된 게 아니라 다르게 짜여 있어도 같은 일을
   하는 함수들이 여러 곳에 있는가. 판단이 필요해 agent가 본다.
3. **방치된 임시 조치** — `TODO`/`임시로` 같은 표시가 남은 채 그 위에 계속 다른 기능이
   쌓여, 되돌리기 비용이 계속 커지고 있는가. 코드가 "언제 생겼는지·그 뒤로 얼마나
   쌓였는지"를 세고, agent는 "이제 되돌리기 비싼가"만 판단한다.

셋 다 검출은 **한 번의 "구조 점검" turn**에서 같이 본다 — bridge가 세 종류의 목록(파일
크기+설계 매핑, 함수 시그니처 목록, TODO 마커+나이/의존도)을 준비해 넘기고, agent가
그것을 보고 finding을 낸다. 고치는 일은 이 앱이 하지 않는다 — Drift와 동일하게
리팩터링 프롬프트를 렌더해 옆 agent에게 건넨다.

**추가 확정 (같은 후속 대화, 저장 형태·이력 수명) — 원본은 `.project-intel/`에 JSON,
이력은 git이 대신한다.** 저장 위치·형식은 이미 있는 패턴(design.json/reviews.json/
wiki 파일들과 동일 — JSON 원본 + 필요하면 `.md` 파생물)을 그대로 따른다. 이력 수명은
Drift와 다르게 간다 — **북마크 없이 매번 현재 상태 전체를 새로 본다.** 같은 파일이
계속 방치돼 있으면 매번 다시 지적돼야 맞고("한 번 지적했으니 다시 안 본다"는 Drift의
논리이지 이 기능의 논리가 아니다), "지난번보다 커졌다" 같은 추세는 git 로그 자체가
이미 갖고 있는 이력이라 별도로 스냅샷을 저장할 필요가 없다. 시각화(§3.2)의 기존 결정
("기능을 실행한 현재 시점의 전체 프로젝트를 분석한 결과")과 같은 방향이다.

함수 시그니처 목록의 토큰 비용에 대해서는 아래 "기능별 컨텍스트 원칙 > 토큰 비용은
항상 줄이는 방향으로"를 참고.

## 기능별 컨텍스트 원칙

기능마다 필요한 자료가 다르므로 모든 기능에 하나의 공통 세션이나 동일한 입력을 강제하지 않는다.

| 기능 | 주된 입력 |
| --- | --- |
| 인터뷰 | 새 프로젝트에 대한 사용자 대화 |
| Wiki | 완성 과정의 에이전트 채팅 기록 + 설명에 필요한 프로젝트 코드 |
| 코드 분석·시각화 | 실행 시점의 프로젝트 코드 전체 |
| Drift | DEC/RULE + 아직 검토하지 않은 커밋 diff |
| 아키텍처·기술부채 | 기존 코드베이스 + 범위가 확정될 프로젝트 기록 |

따라서 기능을 실행할 때 해당 기능 전용으로 필요한 세션, 읽기 권한과 컨텍스트를 구성해야 한다. 프로젝트 디렉터리를 공유한다는 사실은 모든 기능이 같은 대화 기록이나 상태를 공유한다는 뜻이 아니다.

### 기능 실행 시 agent 컨텍스트에 대한 현재 합의

- 앱의 프로젝트 경로가 agent의 `cwd`가 된다.
- 사용자가 기능 버튼을 누르면 우리 앱이 연결된 agent를 실행할 수 있다.
- agent는 기능에 맞는 읽기 범위를 가져야 한다.
- Wiki는 세션 대화와 코드 근거가 필요하다.
- 코드 분석·시각화는 전체 프로젝트 의미를 파악해야 한다.
- Drift는 DEC/RULE과 커밋 diff가 핵심이다.
- 인터뷰는 새 앱에 관한 사용자 대화가 핵심이고 코드 구현 도구는 필요 없다.

기능별로 별도 mode나 세션 키를 사용하는 spike의 격리 메커니즘은 참고할 수 있다. 다만 최종 제품에서 “항상 새 세션”, “항상 기존 세션” 중 하나를 모든 기능에 공통 적용하면 안 된다. 특히 Wiki는 기존 코딩 대화를 읽어야 하므로 새 빈 세션만으로는 입력을 얻을 수 없다.

### 토큰 비용은 항상 줄이는 방향으로 — 일반 원칙 (2026-08-24, 후속 대화)

사용자가 명시했다 — 원문 그대로: "토큰 사용량도 적은 방향으로 가야해." 특정 기능
하나가 아니라 **agent turn을 쓰는 모든 기능에 적용되는 일반 원칙**으로 남긴다.

사실 지금까지도 이 방향으로 해 왔다 — 이미 검증된 두 선례가 있다.

- Wiki: 대화를 40,000자에서 자르고(최근 것을 남긴다), 대상 세션도 최대 10개까지만 본다.
- Drift: 커밋 하나의 diff를 20,000자에서 자르고, 리뷰 대상 커밋도 최대 50개로 캡을 건다.

**agent에게 넘기는 것은 항상 코드가 결정론적으로 요약·정제한 것이지, 원본을 통째로
넘기지 않는다.** 이게 비용을 줄이는 이유이기도 하지만, 원래 목적은 "판단은 agent,
세는 일은 코드"(§3.5) 원칙 자체이기도 하다 — 요약하는 그 과정 자체가 코드가 할 수 있는
결정론적 작업이다. 둘이 같은 방향을 가리킨다.

**질문 5(아키텍처·기술부채)에 적용하면**: 파일 크기 목록과 TODO 마커 목록은 원래도
작아서(파일 수·TODO 개수만큼) 그대로 둬도 된다. **함수 시그니처 목록이 위험 지점이다**
— 큰 프로젝트는 함수가 수천 개일 수 있다. 그래서 이 목록에는:

- 이름과 위치만(본문은 절대 포함하지 않는다).
- 사소한 것(아주 짧은 getter/setter 등)은 걸러낸다.
- 필요하면 Wiki·Drift처럼 상한을 둔다.

"북마크 없이 매번 현재 상태 전체를 본다"는 앞선 결정과는 부딪히지 않는다 — 매번 다시
보는 것은 파일 크기·TODO처럼 원래 작은 목록이고, 커질 수 있는 함수 목록 쪽은 상한으로
누른다.

현재 spike에서 다음은 실제 Codex와 Claude Code 양쪽으로 검증됐다.

- Browser/App이 Agent Adapter를 통해 로컬 agent turn을 시작할 수 있다.
- agent의 작업 디렉터리를 사용자가 지정한 프로젝트 경로로 설정할 수 있다.
- 진행 이벤트를 provider 중립 `AgentEvent`로 정규화해 WebSocket으로 앱에 보낼 수 있다.
- agent가 MCP로 앱 컨텍스트를 읽고 구조화된 결과를 다시 앱에 보낼 수 있다.
- Codex와 Claude의 raw 프로토콜 차이를 Bridge/Adapter 안에 가둘 수 있다.
- 인터뷰, 읽기 전용 리뷰, 읽기 가능한 Wiki turn을 서로 다른 권한과 문서 로딩 정책으로 격리할 수 있다.
- 인터뷰에서 구조화된 설계 원본을 만들고 사람용 문서와 harness를 결정적으로 렌더할 수 있다.
- DEC/RULE 기반 커밋 Drift 판정과 대화 기반 Wiki 용어 추출이 실제 agent에서 동작했다.

제품에 유지할 아키텍처 경계:

```text
App → Agent Adapter → Codex/Claude Code     실행 채널
Agent → MCP → Core/Project Store            컨텍스트·도구 채널
Agent/Bridge → Event Stream → App           진행·결과 채널
```

MCP를 Agent 실행 API처럼 사용하지 않고, App이 파일을 직접 수정하는 코딩 도구가 되지 않는다는 원칙도 유지한다.

### 위 요약을 풀어서 — spike를 만들면서 확정된 것 전부 (협업자용)

위 목록은 결론만 압축한 것이다. 협업자는 이 프로젝트의 대화·문서를 처음 보므로, **왜
그렇게 정했는지**까지 풀어서 남긴다. 출처는 `docs/BYOA_MCP_INTEGRATION_SPIKE.md`와
`prototypes/byoa-mcp-spike/SPIKE_FINDINGS.md`이며, 여기서는 그 내용을 요약하되 걸러내지
않는다 — 이 절이 협업자가 원본 문서 두 개를 처음부터 읽지 않아도 되게 하는 자리다.

#### 1. BYOA(Bring Your Own Agent) — 모델 API를 직접 부르지 않는다

이 제품은 새 코딩 에이전트를 만들지 않는다. 추론은 전부 **사용자가 이미 설치·로그인해 둔
로컬 coding agent**(Codex CLI, Claude Code)가 담당한다. OpenAI/Anthropic 모델 API를
앱 코드에서 직접 호출하는 경로는 어디에도 없고, API key를 입력받는 UI도 없다. 이유는
둘이다 — (1) 제품 포지셔닝이 "특정 모델로 OO를 만들어주는 앱"이 아니라 "선택한 agent를
프로젝트 지식 계층과 연결하는 연동 인프라"여야 하고, (2) 대회 운영규정상 Closed API에
전적으로 의존하는 구조는 제한 대상이지만 연동 인프라 구축 자체는 예외로 인정된다
(`docs/vibe_coding_assistant_design.md` §14, `CLAUDE.md`의 "대회 운영규정" — 2026-08-20
운영사무국 서면 확인).

#### 2. 세 통신 채널을 절대 섞지 않는다

| 채널 | 방향 | 구현 | 무엇을 위한 것인가 |
| --- | --- | --- | --- |
| A. Agent Control | Browser → Agent | HTTP → `codex app-server` JSON-RPC / Claude Agent SDK `query()` | 새 작업을 시작시킨다. **MCP가 아니다.** |
| B. Event Stream | Agent → Browser | agent notification → 정규화 → WebSocket | 진행 상황과 결과를 실시간으로 보여준다. **MCP가 아니다.** |
| C. MCP Tool | Agent → App | agent → stdio MCP server → loopback HTTP → Bridge → WebSocket | agent가 앱 상태를 읽거나 구조화된 결과/판단을 앱에 되돌려준다. |

브라우저는 Codex/Claude의 raw 프로토콜 타입을 절대 보지 않는다 — `packages/protocol`의
`AgentEvent` union 하나로만 정규화되어 올라온다. Phase A(Codex)와 Phase B(Claude) 둘 다
같은 9개 acceptance 항목을 통과했고, **Browser/Bridge protocol을 한 줄도 provider별로
분기하지 않고** provider만 바꿔서 통과시켰다(`SPIKE_FINDINGS.md` §9).

#### 3. "우리는 코드를 쓰는 곳이 아니라 보는 곳이다"

가장 중요한 경계선이다(`docs/BYOA_MCP_INTEGRATION_SPIKE.md` §1.2). 이 앱이 turn을 도는
것 자체는 금지가 아니다 — 인터뷰도, 드리프트 리뷰도, Wiki도 여기서 돈다. 금지되는 것은
**"프롬프트 → 코드 → 확인 → 다음 프롬프트"라는 반복 루프가 이 앱 안에서 도는 것**이다.
그 루프가 여기서 돌기 시작하면 이 앱은 바이브코딩 툴이 되고, 그러면 경쟁 상대가 Codex
자신이 된다 — 에디터·diff 뷰·승인 UI에 이미 훨씬 많이 투자한 상대와 싸우게 되므로 이길
이유가 없다.

비유: **GitHub이 `git`을 대체하지 않는 것과 같다.** `git log`로 다 볼 수 있지만 아무도
그렇게 보지 않는다. GitHub이 하는 일은 같은 데이터에 화면을 주는 것이고, 그 화면의
중심은 저장소가 아니라 PR — 변경을 놓고 판단하는 자리다. 이 제품의 리뷰어는 사람 대신
DEC 목록일 뿐이다.

이 원칙에서 직접 따라 나오는 것들:

- 이 앱이 직접 쓰는 파일은 `.project-intel/`과 인계 산출물(app_design.md, AGENTS.md/
  CLAUDE.md)뿐이다. GitHub이 직접 쓰는 것이 git 메타데이터뿐인 것과 같다. **소스 코드는
  항상 옆 창(사용자의 Codex/Claude Code)이 쓴다.**
- Drift가 어긋난 것을 찾아도 이 앱이 고치지 않는다 — 고칠 프롬프트를 렌더해서 건넨다
  (§3.3의 해소 프롬프트).
- `mode: "task"`(spike에서 파일을 직접 수정하는 유일한 경로)는 예외가 아니라 **검증
  장치**다. Phase A/B가 "Agent Control 채널이 살아 있는가"를 확인하려고 만든 것이고,
  acceptance가 계속 그것만 잰다. **제품 경로가 아니며 그 위에 기능을 쌓지 않는다.**
- 이 선은 실용적인 이득이기도 하다 — 실행을 이 앱이 독점하면 이 앱이 adapter를 만든
  도구에서만 쓸 수 있다. 프롬프트를 건네는 경로는 adapter가 없는 도구에도 붙는다. 그것이
  "연동 인프라"라는 포지셔닝이 말뿐이 아니게 되는 유일한 방식이다.

#### 4. mode 격리 — 코드를 쓰는 mode는 `task` 하나뿐이다

spike는 `task`/`interview`/`review`/`wiki` 네 가지 실행 모드를 만들었고, 각 모드가
project 문서 자동 로딩·내장 도구·sandbox를 다르게 받는다(`isReadOnlyMode`,
`needsReadTools`).

| mode | sandbox | 프로젝트 문서(AGENTS.md/CLAUDE.md) 자동 로딩 | 내장 도구 | 왜 |
| --- | --- | --- | --- | --- |
| `interview` | read-only | **안 읽음** | 없음 (MCP tool만) | 하네스를 읽으면 "앱을 끝까지 만들어라"를 인터뷰 turn이 따르기 시작한다(§14 finding) |
| `task` | workspace-write | 읽음 | 전부 | 유일하게 코드를 쓰는 mode. **검증 장치이지 제품 경로가 아니다** |
| `review` | read-only | 안 읽음 | 없음 | 하네스를 읽으면 "어긋난 것을 보고" 대신 "고치기 시작"한다(실측 확인) |
| `wiki` | read-only | 안 읽음 | Read/Grep/Glob만 | 근거(`where`)를 확인하려면 코드를 읽어야 하지만, 고치면 안 된다 |

같은 프로젝트 디렉터리에서도 mode별로 **별도 thread/session**을 쓴다(`threadKey`/
`sessionKey`가 `(프로젝트 경로, mode)`로 캐싱). 안 그러면 작업 turn이 인터뷰 문답
전체를 문맥에 안고 시작하는 것 같은 오염이 생긴다. 이 mode 경계가 **§3.3/§3.5의 "판단은
agent가, 나머지는 코드가" 원칙과 §1.2의 "우리는 보는 곳" 원칙을 코드 레벨에서 강제하는
장치**다.

#### 5. MCP tool 인벤토리 — 지금까지 실제로 만들어 검증한 것

| tool | 무엇을 위한 것인가 | 어느 mode에서 |
| --- | --- | --- |
| `get_app_context` | 앱의 현재 상태(프로젝트 경로, 선택 항목, 인터뷰 문답, 설계 요약) 조회 | `task` (spike 검증용) |
| `show_result` | 자유 텍스트 대신 구조화된 결과를 앱에 push | `task` (spike 검증용) |
| `ask_user` | 질문 하나를 등록하고 즉시 turn을 끝낸다(블로킹 안 함) | `interview` |
| `save_design` | 일곱 단위(ACTOR/REQ/SURFACE/ENTITY/FLOW/RULE/DEC) 전체를 저장 | `interview` |
| `get_review_context` | 리뷰 대상 커밋들의 diff + DEC/RULE 기준 전체를 받는다 | `review` |
| `report_drift` | 커밋별 위반 판정(findings)을 되돌려준다. 위반이 없어도 반드시 호출 | `review` |
| `get_wiki_transcript` | 코드 블록·래퍼를 걷어낸 대화 전문을 받는다 | `wiki` (키워드 단계) |
| `save_wiki_keywords` | 판단으로 고른 후보 키워드(용어·이유·예문)를 저장 | `wiki` (키워드 단계) |
| `get_wiki_context` | 그 용어가 나온 대화 대목 + 설계 원본을 받는다 | `wiki` (페이지 단계) |
| `save_wiki` | 완성된 위키 페이지(한 줄 설명, 이 프로젝트에서의 의미, 근거, 관련 용어)를 저장 | `wiki` (페이지 단계) |

모든 tool 호출은 **서로 독립적인 두 증거원**으로 확인한다 — agent 자신이 보고한
`agent-stream` 증거와, 별도 프로세스로 뜬 MCP server가 실제로 loopback HTTP로 Bridge를
호출한 `bridge-endpoint` 증거. 한쪽만 있으면 실패로 본다(`SPIKE_FINDINGS.md` §4). MCP
호출을 mock하거나 Bridge가 결과를 임의로 만들어낸 적은 없다.

#### 6. Codex와 Claude — 같은 인터페이스, 다른 구현

`AgentAdapter` 인터페이스 하나로 두 provider를 추상화했다. 실제로 Phase B에서는 adapter를
추가하고 등록한 것 외에 Bridge의 HTTP/WebSocket 계층, `AgentEvent`, MCP server를
**전혀 건드리지 않고** 같은 acceptance 9개 항목을 통과시켰다. 다만 provider 내부 구현은
다르다.

| | Codex | Claude |
| --- | --- | --- |
| Agent control | `codex app-server` child process + JSON-RPC | Agent SDK `query()` |
| MCP 등록 | 전역 `codex mcp add` 필요 (`npm run mcp:register`) | **불필요** — `options.mcpServers`로 query마다 직접 전달, `strictMcpConfig: true`로 사용자의 다른 MCP 설정과 격리 |
| 다른 MCP 서버 격리 | elicitation 요청에서 `serverName`을 보고 우리 서버만 수락 | 애초에 `strictMcpConfig`로 로드조차 안 됨 |
| 도구 승인 | `mcpServer/elicitation/request` 응답 | `canUseTool` 콜백 |
| 세션 재사용 | 프로젝트당 thread 하나 (`thread/start`/`thread/resume`) | 프로젝트당 `session_id` 하나 (`options.resume`) |
| 중단 | `turn/interrupt` (정상 흐름의 status로 구분) | `AbortController.abort()` (예외로 끝나서 별도 처리 필요했다 — Finding 7) |
| 쓰기 범위 강제 | OS 레벨 `sandboxPolicy.writableRoots` | 없음 — `canUseTool`에서 Write/Edit 경로만 직접 검사. **Bash로 프로젝트 밖에 쓰는 것은 막지 못한다**(Finding 6). 이 격차는 `task` mode에만 있고, `task`는 제품 경로가 아니라 검증 장치이므로 제품이 이 격차를 물려받지 않는다 |
| CLI에서 이어받기 | `codex resume` 목록에 그대로 뜬다 | SDK가 만든 세션은 `claude --resume` picker에 **안 뜬다**(Finding 8) — `claude -c` 또는 세션 ID 직접 지정만 된다. 그래서 UI가 세션 ID를 노출하고 복사 버튼을 둔다 |

#### 7. Safety / Cleanup 불변조건

Phase A acceptance를 통과한 뒤에도 계속 유지해야 하는 것들이다.

- Bridge와 MCP server는 `127.0.0.1`에만 bind (외부 네트워크에 공개하지 않음)
- `/internal/*`는 로컬 전용 토큰(`x-byoa-token`)으로 보호된다
- Stop 버튼으로 active turn을 interrupt할 수 있다
- `npm run mcp:unregister`로 등록을 완전히 제거할 수 있다
- prototype 종료 후 child process가 남지 않는다 (SIGTERM → 2초 후 SIGKILL, 윈도우는
  `taskkill /T /F`)
- project path는 canonicalize하고, 선택된 프로젝트 root 밖을 임의로 writable root로
  추가하지 않는다
- API key를 브라우저 localStorage에 저장하지 않는다 (애초에 API key를 다루지 않는다)
- 사용자의 Codex/Claude 인증 credential을 직접 읽거나 복사하지 않는다 (Codex는
  `account/read` 응답으로 인증 여부만 확인, 이메일 등은 브라우저로 보내지 않는다)
- 사용자의 전역 Codex/Claude 설정을 자동으로 덮어쓰거나 초기화하지 않는다 — 등록은
  `codex mcp add byoa-spike ...` 한 줄이 전부이며, 기존 MCP 설정을 읽지도 덮어쓰지도
  삭제하지도 않는다

#### 8. 검증 결과 요약 (Phase A~F)

| Phase | 무엇을 확인했나 | 결과 |
| --- | --- | --- |
| A (Codex) | Agent Control/Event Stream/MCP 세 채널이 실제로 동작 | acceptance 9/9 |
| B (Claude) | 같은 채널을 provider만 바꿔서 확인 | acceptance 9/9, Bridge/Browser 코드 무변경 |
| C (인터뷰 루프) | 질문→turn 종료→답변→다음 turn이 문맥을 이어받는 구조 | 두 provider 통과 |
| D (인터뷰 이후 전체 플로우) | 일곱 단위 추출, 사람용 설명·harness의 결정론적 렌더, 인계 | `npm run interview` 15/15 |
| E (Drift 검출·해소) | 커밋 단위 위반 검출 + 오탐 없음 + 해소 프롬프트로 코드/결정 중 정확히 한쪽만 고쳐짐 | 검출 4/4·오탐 없음 4/4, 해소 3/3(두 provider) |

#### 9. 아직 풀리지 않은 spike 수준의 함정

- **윈도우 실기 검증 미완료.** 코드는 `.cmd` spawn, `killTree()` 등으로 고쳤지만 실제
  윈도우 머신에서 `npm run acceptance`를 돌려보지 못했다(Finding 9).
- **Claude의 Bash 쓰기 범위 제한 격차.** `canUseTool`이 Write/Edit는 막지만 Bash로
  프로젝트 밖에 쓰는 것은 못 막는다. `task` mode에만 있는 격차라 제품이 물려받지는
  않는다(Finding 6).
- **thread/session이 계속 쌓인다.** Bridge를 재시작할 때마다, 또는 판단형 turn마다 새
  세션을 만들면 사용자의 `codex resume` / `claude --resume` 목록이 이 앱이 만든 세션으로
  계속 채워진다. 질문 4를 "sitting 단위"로 다듬으면서(아래) 누적 속도는 늦췄지만
  (Wiki는 후보 클릭마다가 아니라 패널을 열 때만 새 세션) **없앤 것은 아니다** — Drift는
  여전히 리뷰 한 번마다 새 세션이 쌓인다. Codex의 `thread/start`가 지원하는
  `ephemeral: true`(디스크에 안 남기는 옵션, `SPIKE_FINDINGS.md` §7)나 Claude SDK의
  `persistSession: false`(같은 목적의 옵션, `node_modules/@anthropic-ai/claude-agent-sdk`
  타입 정의에서 확인)를 판단형 mode(`review`/`wiki`)에 적용하면 이 문제 자체가 사라질
  수 있다 — 이 turn들은 애초에 `codex resume`/`claude --resume`으로 이어받을 이유가
  없는 turn들이므로, SPIKE_FINDINGS §7이 지적한 "이력 보존과 오염 방지는 맞바꿈 관계"의
  손해 볼 쪽(이력 보존)을 애초에 원하지 않는 경우다. **아직 코드로 확인하지 않았다** —
  두 옵션 다 실제로 동작하는지, 그리고 `report_drift`/`save_wiki`가 이미 bridge 쪽에
  기록을 남기므로(`reviews.json`, `.project-intel/wiki/*.json`) agent 세션 쪽 이력이
  없어도 "무엇을 했는지"가 유실되지 않는지 확인이 필요하다.
- **MCP tool 승인이 사용자에게 노출되지 않는다.** 지금은 Bridge가 정책으로 자동
  수락/거부한다. 제품에서는 승인 UI(허용/거부, 세션 기억)가 필요하다.
- **드리프트 리포트의 수명 관리가 얕다.** "열림 → 승인됨/수정됨/무시됨" 같은 상태
  기계 없이, 커밋 단위 재검토 없음으로만 관리한다 — 지금까지는 충분했지만 결정이
  자주 갱신되는 프로젝트에서도 그런지는 안 봤다.

다음 문구들은 역사적 설계 또는 spike 요구사항으로는 의미가 있지만, 현재 제품 플로우의 확정 사항으로 그대로 사용하면 안 된다.

## 더 이상 전제로 삼지 않는 초기 구상

- 인계 후 우리 앱에서 인터뷰를 이어서 설계를 다시 내보내는 흐름
- 인터뷰와 Drift를 하나의 기능 수명주기로 보는 구조
- 모든 기능을 하나의 end-to-end cycle로 묶는 구조
- 완성된 프로젝트를 우리 앱에 다시 import하거나 연결하는 별도 단계
- 모든 분석 결과를 커밋 변경에 맞춰 함께 무효화하거나 자동 갱신하는 구조
- Wiki를 코드 변경 감시나 의사결정 평가 기능으로 보는 설명

추가로 다음 질문도 이미 답이 나왔으므로 반복하지 않는다.

- “완성된 프로젝트를 어떤 방식으로 다시 import할 것인가?” → import하지 않는다. 같은 워크스페이스다.
- “커밋이 바뀌면 Wiki·코드 분석·아키텍처 결과를 모두 어떻게 무효화할 것인가?” → 공통 무효화 전제가 잘못됐다.
- “인계 후 설계를 우리 앱의 인터뷰에서 다시 고칠 것인가?” → 아니다. 연결된 코딩 에이전트가 담당한다.
- “Wiki는 작업 하나가 끝날 때마다 실행하는가?” → 작은 작업 완료가 기준이 아니다. 최초 end-to-end 결과물 전체가 완성된 이후가 출발점이다.
- “코드 분석은 이전 결과를 계속 유지·동기화하는가?” → 사용자가 기능을 실행할 때 현재 전체 코드를 새로 분석하는 것이 사용자 기준이다.

## 아직 정하지 않은 것

- 프로젝트 디렉터리를 지정한 직후 보여줄 첫 화면과 기능 진입 방식 — **후속 대화에서
  확정.** 프로젝트 상태 감지로 화면을 다르게 보여주고, 이미 설계가 있는 프로젝트에서는
  인터뷰가 "이어서 고치기"로는 아예 등장하지 않으며 "지우고 새로 시작"만 경고와 함께
  드문 예외로 남는다. 질문 6 참고.
- 기능별 세션을 새로 만들지, 기존 에이전트 세션 중 무엇을 선택할지에 대한 규칙 —
  **후속 대화에서 확정.** 아래 "후속 결정" 절의 질문 4 참고.
- 여러 코딩 세션 가운데 Wiki가 분석할 대화를 정하는 방식 — **후속 대화에서 확정.** 아래
  "후속 결정 (2026-08-24, 같은 세션 이어서)" 절에 질문·답변·근거를 전부 남겨 둔다.
- 아키텍처·기술부채 분석의 정확한 입력, 결과 형식과 이력 수명 — **후속 대화에서 확정**
  (범위는 파일 비대화·의미 중복·방치된 임시 조치 셋, 저장은 기존 패턴 재사용, 이력은
  북마크 없이 매번 현재 스냅샷 + git이 추세를 대신함. 질문 5 참고).
- 각 기능의 결과를 앱과 `.project-intel/` 중 어디에 어떤 형태로 저장할지 — 아키텍처·
  기술부채에 대해서는 위에서 확정(기존 JSON+MD 패턴 재사용). 다른 아직 안 만든 기능
  (시각화 등)에 일반화한 것은 아니다.
- 기능 실행 전 코드 전체를 읽는 방식과 큰 프로젝트에서의 컨텍스트 분할 전략 — 질문 5가
  아키텍처·기술부채 하나에 한해 초안(목록만 결정론적으로 뽑아 agent에게 준다)을
  제시했지만, 다른 기능(시각화 등)까지 아우르는 일반 규칙으로 확정한 것은 아니다.

## 다음 대화의 권장 시작점

다음 에이전트는 프로젝트 첫 화면을 추상적으로 다시 묻기보다, **기능별 실행 버튼을 눌렀을 때 어떤 자료와 어떤 agent session을 선택해야 하는지**부터 좁히는 것이 좋다.

가장 가까운 미정 지점은 Wiki다. Wiki는 전체 결과물이 완성된 뒤 코딩 채팅을 분석하지만 실제 프로젝트에는 다음이 있을 수 있다.

- 인터뷰 세션
- 최초 전체 구현 세션
- 중간에 새로 시작한 여러 코딩 세션
- Codex와 Claude Code 중 하나 또는 둘의 세션
- 이후 확장 작업 세션

따라서 다음 질문은 한 번에 하나만 한다. 예를 들면 다음 지점을 먼저 물을 수 있다.

> Wiki를 실행했을 때 앱이 분석해야 할 대화 범위를 사용자가 직접 고르게 할지, 같은 프로젝트의 최초 구현 관련 세션을 앱이 찾아 한데 모을지?

이 질문을 정한 뒤에 세션 발견 방식, provider별 기록 접근, 코드 근거 조회, 저장 수명을 순서대로 정한다. 아키텍처·기술부채 기능의 정확한 사용자 목표와 결과 수명도 별도의 후속 논의로 남겨 둔다.

## 후속 결정 (2026-08-24, 같은 세션 이어서)

이 문서를 쓴 직후, 같은 대화가 이어져 위에서 "다음 대화의 권장 시작점"으로 제안해 둔
질문에 실제로 답이 나왔다. 이 절은 그 대화 자체를 남긴다 — **이 문서는 협업자와도
공유하므로, 확정됐다고 앞의 논의 과정을 지우지 않는다.**

### 질문 1 — Wiki 세션 범위: 사용자가 고르나, 앱이 모으나?

바로 위 "다음 대화의 권장 시작점"이 던진 질문 그대로다. 실제 spike 코드를 다시 확인하니
**이미 구현되어 검증까지 끝나 있었다** — `apps/bridge/src/agents/{codex,claude}/adapter.ts`의
`readTranscript()`가 프로젝트 디렉터리 기준으로 최근 세션 최대 10개를 자동으로 모은다
(우리 앱이 시작한 대화든 사용자가 옆 창에서 CLI로 직접 한 대화든 함께). 사용자에게 "어느
세션을 볼까요"를 묻는 UI는 없다.

**확정**: 세션 범위는 사용자가 고르지 않는다. 앱이 자동으로 모은다. (spike 구현을 그대로
제품 결정으로 승격 — 이미 검증됐고, "버튼 누르면 바로 후보가 뜬다"는 원래 취지에도 맞는다.)

### 질문 2 — Codex로 만들고 Claude로 Wiki를 누르면?

질문 1을 확인하는 과정에서, 두 provider의 세션 저장소가 완전히 분리돼 있다는 것을 다시
확인했다(Codex는 `thread/list`, Claude는 `~/.claude/projects/`의 `.jsonl` 파일). 이걸 보고
에이전트(나)가 먼저 이렇게 물었다.

> "사용자가 최초 구현은 Codex로 하고 나중에 Wiki를 Claude 선택 상태에서 누르면, Claude
> 쪽에는 그 대화가 아예 없어서 '설명할 만한 말이 없었습니다'로 조용히 끝나 버립니다.
> Wiki가 읽는 대화는 선택된 agent와 무관하게 두 provider 세션을 다 모으는 쪽이 맞지
> 않을까요?"

사용자가 이 전제 자체를 기각했다 — 원문 그대로:

> "그건 내가 생각해봤을 때 비전공자라면 한번에 하나의 플랫폼만 구독할거라 생각했거든
> 그래서 코덱스 사용자는 코덱스거만 보는게 맞다 생각했어"

**확정**: provider를 넘나들며 세션을 합치지 않는다. Codex 사용자는 Codex 세션만, Claude
사용자는 Claude 세션만 본다. 근거는 이 프로젝트가 이미 갖고 있던 사용자 전제
(`docs/requirements_flow.md` §2 "사용자는 도구를 하나만 쓴다" — 비전공자는 귀찮아서
도구를 하나만 골라 쓴다)다. 두 provider를 섞어야 하는 문제는 **이 전제 위에서는 실제로
일어나지 않는 상상의 엣지 케이스**였다. 코드 변경은 필요 없다 — 이미 그렇게 동작한다.

### 질문 3 — 세션을 매번 다시 훑나, "마지막으로 본 지점" 이후만 보나?

질문 1·2를 정리하다가 에이전트(나)가 이어서 제기한 질문이다.

지금 spike 구현은 Wiki를 실행할 때마다 "이 프로젝트 디렉터리 + 지금 선택된 provider"
조건으로 최근 세션을 매번 새로 찾는다 — Drift처럼 `lastReviewedSha` 같은 북마크가 없다.
세션이 쌓이면 오래된 세션은 "최근 10개" 창 밖으로 자연히 밀려난다.

**에이전트(나)의 첫 추천 (기각됨): 북마크를 두지 말고 지금처럼 매번 최근 창만 본다.**
근거로 든 것은 Drift와 Wiki가 다루는 대상의 성격이 다르다는 것 — Drift의 커밋은 불변이라
"이미 본 건 다시 안 본다"가 맞지만, Wiki는 "아까 걔가 말한 그게 뭔데"라는 **최근성 자체가
기능의 정의**라고 주장했다.

사용자가 이 추천을 기각했다 — 원문 그대로:

> "음 근데 최근성도 중요한 것 맞는데 애초에 지금 방식이 대화 기록 분석해서 키워드로
> 제공하는 거 잖아. 그렇다면 이전 모든 대화기록을 가져와야하지 않을까?"

되짚어 보니 이 지적이 맞다. §3.5의 예시(인메모리 저장소 — `user.js`/`item.js`/`rental.js`
전반에서 쓰이는 용어)부터가 "방금 나온 말"이 아니라 **빌드 전체에서 쓰인 말**을 완성 후
한 번에 훑어보는 그림이다. 그리고 "최근 10개까지" 캡은 애초에 그런 의도로 넣은 것도
아니었다 — spike 코드 주석은 "대화가 쌓여도 비용이 선형으로만 늘게 한다"고만 적혀 있다.
비용 때문에 넣은 임시 방편을 사후에 "최근성이 곧 기능의 정의"라고 정당화한 것이었다.
세션이 10개 넘게 쌓이면 초반 세션의 용어가 영영 후보에 못 오르는 지금 동작은 설계가
아니라 결함에 가깝다.

**확정 — 북마크 기반 증분 수집.** Drift의 `lastReviewedSha`와 같은 모양이다.

- 처음 Wiki를 누르면 그때까지의 **모든** 세션을 읽는다 (Drift가 design.json이 들어온
  커밋부터 전부 보는 것과 같다).
- 그 다음부터는 마지막으로 본 지점 이후의 **새 세션만** 읽어서, 이미 모아 둔 후보 목록에
  더한다. 오래된 세션을 놓치는 일이 없다(한 번은 반드시 읽는다) — 그러면서도 매번 전체를
  다시 읽지 않으니 비용이 세션 수만큼 곱해지지도 않는다.
- 후보는 그 자리에서 뽑고 버리는 것이 아니라, 아직 페이지로 만들지 않은 것들을 계속
  쌓아 둔다 — 페이지를 만든 후보만 목록에서 빠진다.

이미 검증된 Drift의 패턴을 그대로 재사용하는 것이라 새 메커니즘을 발명할 필요는 없다.
다만 spike 코드(`readTranscript()`의 세션 상한, `condenseTranscript()`의 문자 수 상한이
전체 이력이 아니라 최근 것을 남기는 방향으로 자르는 로직)에 아직 반영하지 않았다 —
지금은 제품 결정만 확정한 상태다.

### 질문 4 — 기능마다 세션을 새로 만드나, 있던 걸 계속 쓰나?

"아직 정하지 않은 것" 목록의 "기능별 세션을 새로 만들지, 기존 에이전트 세션 중 무엇을
선택할지에 대한 규칙"에 대한 답이다.

spike 코드를 확인해 보니 이미 애매하게 동작하고 있었다. Codex/Claude 두 adapter 모두
세션(thread)을 `(프로젝트 경로, mode)` 조합으로 캐싱해서 재사용한다
(`apps/bridge/src/agents/codex/adapter.ts`의 `threadKey`/`ensureThread`,
Claude 쪽의 `sessionKey`도 같은 모양). 그래서 같은 프로젝트에서 Drift 리뷰를 열 번 돌리면
**열 번이 전부 같은 대화(같은 thread) 안에서** 일어난다 — 매 리뷰가 `get_review_context`로
필요한 것(diff, 기준)을 새로 받아 가니 판정 자체는 맞지만, 지난 리뷰들의 대화 기록이
문맥에 계속 쌓인다. 인터뷰 초안을 매 turn 다시 돌려주면 안 된다고 이미 확인했던 것
(§4.11 관련, `SPIKE_FINDINGS.md` §14)과 같은 종류의 낭비다.

실제로 `scripts/drift.mjs`를 여러 번 반복 실행(`npm run drift codex 3` 같은)할 때도, 매 실행마다
`createDriftFixture()`가 완전히 새로운 fixture(새 커밋들)를 만드는데 리뷰 세션은 재사용되고
있어서, 이전 실행에서 이미 지워진 커밋 이야기가 다음 리뷰의 문맥에 그대로 남아 있었을
것이다.

**첫 확정 (수정됨)**: 기능을 대화가 이어져야 하는 것과 매번 완결되는 판단인 것으로 나눠서
다르게 다룬다.

- **대화가 이어져야 하는 기능 — 세션을 계속 재사용한다.** 인터뷰(질문과 답이 서로를
  참조해야 한다), 최초 전체 구현(하나의 연속된 코딩 작업).
- **매번 완결되는 판단인 기능 — 매번 새 세션으로 시작한다.** Drift 리뷰, Wiki 키워드
  추출, Wiki 페이지 작성. bridge가 그때그때 필요한 것을 MCP tool로 전부 넣어주므로 지난
  실행을 기억할 이유가 없다.

#### 수정 — "판단 단위"가 아니라 "사용자가 이어서 하고 있는 한 덩어리(sitting)" 단위다

사용자가 위 확정에 이어서 지적했다 — 원문 그대로:

> "위키 패널을 열어두고 후보 A, B, C를 연달아 누를 때 그게 '한 세션'처럼 느껴져야
> 한다는 UX 얘기였어"

맞는 지적이다. **판단 단위와 사용자 상호작용 단위가 항상 같지 않다.** Drift는 버튼
한 번이 곧 리뷰 한 번으로 끝나서 둘이 같지만, Wiki는 버튼 한 번(패널 열기 → 후보 목록
받기)이 그 뒤로 후보 A/B/C를 하나씩 눌러 페이지를 쓰는 **여러 번의 판단으로 이어진다.**
"매번 새 세션"을 문자 그대로 적용하면 후보를 하나 누를 때마다 세션이 생겨서, 방금 정한
"세션이 계속 쌓이는" 문제를 오히려 악화시킨다 — 게다가 사용자 입장에서도 한 번의 위키
탐색이 부자연스럽게 조각난다.

**최종 확정**: 세션을 새로 만드는 기준은 "판단 하나"가 아니라 **"사용자가 계속 이어서
하고 있는 한 덩어리(sitting)"**다.

- **Drift** — 리뷰 한 번이 곧 sitting 하나다. 원래 확정대로 매번 새 세션.
- **Wiki** — 후보 목록을 새로 뽑는 순간(`/api/wiki/keywords`, 곧 질문 1의 "북마크 기반
  증분 수집"이 새 라운드를 시작하는 시점과 같다)에만 새 세션을 만든다. 그 목록에서 후보를
  몇 개를 연달아 눌러 페이지를 쓰든(`/api/wiki`) **같은 세션을 계속 쓴다.** 다음에 다시
  위키를 열어 새 후보 목록을 뽑을 때(= 새 sitting) 그때 세션을 새로 만든다.

이렇게 하면 세션 누적 속도도 "후보를 누른 횟수"가 아니라 "위키를 연 횟수"에 비례하게
되어, 방금 §9(아직 풀리지 않은 spike 수준의 함정)에서 지적한 누적 문제도 함께 완화된다.

이것도 spike 코드(`threadKey`/`sessionKey`의 캐싱 로직, `/api/wiki/keywords` 시작 시
명시적 reset 추가)에는 아직 반영하지 않았다 — 제품 결정만 확정했다.

### 질문 5 — 아키텍처·기술부채가 정확히 뭘 하는 기능인가?

사용자가 먼저 인정했다 — 원문 그대로: "사실 해당 개념은 이해가 잘 안가는 부분이야 내가."
Drift 때와 같은 패턴이다(§3.3 논의 초반에도 "drift 관리가 정확히 뭔지 잘 모르겠다"는
말이 있었다) — 개념이 안 잡히면 설계를 진행할 수 없으므로, 추상적 정의 대신 사용자의
실제 경험을 먼저 물었다.

#### 왜 Drift와 다른가

에이전트(나)가 먼저 구분을 제시했다 — Drift(§3.3)는 "이 커밋이 명시적으로 정한 결정
(DEC/RULE)을 어겼는가"를 보는데, 이건 **개별 커밋 하나만 보면 위반이 없는** 문제를
못 잡는다. 바이브코딩에서 실제로 흔한 문제는 "아무도 하지 말라고 말한 적이 없는데
코드의 모양이 여러 커밋에 걸쳐 조금씩 나빠지는 것"이고, 비전공자는 코드를 못 읽으니
스스로 알아챌 방법이 없다.

#### 사용자가 확인한 실제 경험

에이전트(나)가 예시 셋을 먼저 제시했다.

> - 처음엔 작았던 파일 하나에 기능을 붙일 때마다 계속 이어붙여서, 50번째 turn쯤엔 그
>   파일 하나가 3000줄이 되고 앱의 거의 모든 걸 건드리게 됨 (아무도 "한 파일에 다 넣지
>   마세요"라고 DEC을 만든 적은 없음)
> - "일단 이렇게 임시로 처리, 나중에 정리" 같은 TODO가 남았는데, 그 위에 다른 기능
>   40개가 계속 쌓여서 이제는 되돌리기가 거의 불가능해짐
> - 비슷한 로직을 매번 새로 복붙해서 만들다 보니, 나중에 하나 고치면 다른 다섯 군데는
>   그대로 남아 어긋남

사용자가 실제로 겪었다고 확인했다 — "실제로 지금까지 만들면서... 이런 걸 겪어보신 적
있나요? -> 이거 있는 거 같아", 이어서 구체적으로 "하나의 코드에 너무 많은 코드가
쌓이는 것"을 콕 짚었고, "이런건 리팩터링으로 해결할 수 있을 거 같은데"라고 스스로
해소 방향까지 제시했다. 그다음 "같은 기능을 하는 함수가 여러 코드에 존재할 수도 있을
것 같고"를 추가했고, 마지막으로 위 세 예시(에이전트가 처음 제시했던 것) 전부를
"이거까지 생각해보자"며 다시 가져왔다.

#### 정리 — 검출은 셋, 해소는 하나

**해소는 이미 Drift와 같은 자리다.** 사용자가 스스로 짚었듯("리팩터링으로 해결") 이
앱이 리팩터링을 하지 않는다 — 발견하면 고칠 프롬프트를 렌더해서 옆 agent에게 건넨다.

**검출 쪽에서 짚은 원칙 하나**: 단순 크기/줄 수 임계값 같은 범용 기준은 이미 옆 agent가
알고 있는 범용 베스트프랙티스라서, 이 제품이 만들 이유가 약하다(Drift가 "버그·스타일은
agent 몫"이라고 정한 것과 같은 논리). 이 제품의 몫은 **agent가 스스로는 안 물어보는
"잠깐 멈춰서 구조를 점검하는" 순간을 대신 챙겨주는 것**이고, 판단 기준은 범용이 아니라
**이 프로젝트 고유의 것**(인터뷰 산출물)이어야 Drift와 같은 결이 된다.

**확정된 세 가지 검출 대상**과 각각의 검출 방식:

| 증상 | 코드가 결정론적으로 준비하는 것 | agent가 판단하는 것 |
| --- | --- | --- |
| 파일/모듈 비대화 | 파일 크기 + 설계 ENTITY/REQ와의 매핑 | 코드 구조가 설계 경계를 아직 따르는가 |
| 의미가 같은 로직 중복 | 함수/메서드 시그니처 목록(위치 포함) | 텍스트는 달라도 같은 일을 하는 함수가 있는가 (Wiki의 판단-기반 추출과 같은 이유 — 텍스트 유사도만으로는 못 잡는다) |
| 방치된 임시 조치 | `TODO`/`임시로` 마커 grep + git blame로 나이·그 뒤에 쌓인 커밋 수 | 이제 되돌리기 비용이 커졌는가 |

셋 다 **한 번의 "구조 점검" turn**에서 같이 판단한다 — 세 목록을 함께 받아 finding을
내고, Drift와 동일한 방식으로 해소 프롬프트를 렌더한다.

**범위 밖으로 뺀 것**: 기존 문서(README/설계 문서)에 후보로 적혀 있던 의존성 증가·
결합도·응집도·순환 의존성·레이어 위반은 이번 범위에서 뺐다 — 위와 같은 이유(범용
베스트프랙티스)다. 필요해지면 별도 논의로 다시 연다.

**코드 전체 읽기 전략과의 연결**: "구조 점검" turn이 코드 전체를 agent에게 그대로
던지지 않고 **결정론적으로 뽑은 목록만 준다**는 이 설계가, "아직 정하지 않은 것"의
마지막 항목("기능 실행 전 코드 전체를 읽는 방식과 큰 프로젝트에서의 컨텍스트 분할
전략")에 대한 초안 답이 될 수 있다. 다만 이 항목 자체를 확정한 것은 아니다 — 여기서는
아키텍처·기술부채 기능 하나에 한해 방향만 잡았다.

**갱신 (2026-08-24, 다른 세션이 spike에 구현)**: 이 절을 쓸 때는 spike에 반영된 적이
없었지만, 같은 날 다른 세션이 위 결정 그대로(세 카테고리, 목록만 결정론적으로 준비,
해소 프롬프트 handoff, sitting마다 새 세션, 현재 snapshot 덮어쓰기) `apps/bridge/src/
architecture.ts`에 구현했다. 이어진 대화에서 그 구현을 리뷰하고, 회귀 검증 스크립트
추가와 토큰 캡 보강까지 마쳤다 — 자세한 내용과 실측 결과는 아래 "후속 결정"의 질문 7,
그리고 `SPIKE_FINDINGS.md` §17에 있다.

### 질문 6 — 프로젝트 디렉터리를 지정한 직후 첫 화면은 무엇을 보여주나?

"아직 정하지 않은 것" 목록의 마지막 항목이다.

에이전트(나)의 제안: 첫 화면을 고정된 메뉴로 두지 않고 **프로젝트 상태를 감지해서
다르게 보여준다.** `.project-intel/design.json`이 없고 코드도 거의 없으면 새 프로젝트로
보고 "인터뷰 시작"을 자연스러운 첫 행동으로 보여준다. design.json이 있거나 코드가 이미
있으면 후속 기능(Drift/Wiki/시각화/기술부채) 버튼들을 보여준다 — 이 감지는 이미 각
기능이 서버에서 하고 있는 전제 검사(`/api/review`가 design.json 없으면 400을 주는 것
같은)를 실행 전에 미리 화면에 반영하는 것뿐이라 새 로직이 크지 않다.

이 논의 중에 안전 문제 하나를 같이 발견했다 — **이미 설계·코드가 있는 프로젝트에서
"인터뷰 시작"을 눌러도, 지금 코드는 조용히 기존 `app_design.md`/harness/
`.project-intel/`을 지우고 새로 시작한다**("새 인터뷰 = 새 프로젝트"가 의도된 동작이지만
사용자가 실수로 누르면 파괴적이다). 그래서 이미 설계가 있는 프로젝트에서는 "인터뷰
시작"을 기본 동작으로 그냥 보여주지 말고, 눌렀을 때 "지금 것을 지우고 완전히 다른
앱을 새로 시작합니다" 같은 명시적 경고를 걸어야 한다고 제안했다.

**확정**: 상태 감지로 화면을 다르게 보여주고, 이미 설계가 있는 프로젝트에서의 인터뷰
재시작은 경고를 거는 위험 행동으로 취급한다.

사용자가 여기에 더 강한 제약을 하나 얹었다 — 원문 그대로: "유저 시나리오에서 인터뷰로
다시 돌아오는건 없는 거야. 인터뷰 끝나고 설계변경은 에이전트 앱에서 이어가는거니까."

**추가 확정**: 이미 설계가 있는 프로젝트의 첫 화면에 "인터뷰로 돌아가서 이어서
고치기" 같은 선택지는 **아예 없다.** §3.1이 인계로 끝난 뒤 설계를 더 고치고 싶으면
연결된 Codex/Claude Code가 `.project-intel/design.json`을 직접 고치는 것이지(질문
4·5에서 반복 확인된 원칙), 우리 앱의 인터뷰로 돌아오는 경로가 아니다. 그러므로 위
"경고를 거는 위험 행동"의 정확한 의미는 **"이어서 고치기"가 아니라 "지우고 완전히
다른 앱을 새로 만들기"** 하나뿐이다 — 그 외에는 인터뷰 자체가 화면에 등장하지 않는다.

spike의 "기존 대화 이어가기" UI(어떤 세션이든 골라 이어받는 기능)는 이 결정과 정면으로
안 맞는다 — 인터뷰 세션을 골라 이어받는 것이 이제는 없는 시나리오이기 때문이다. 이
UI를 제품에 그대로 가져갈지, 가져간다면 인터뷰 mode는 목록에서 빼야 하는지는 아직
따로 정하지 않았다.

## 배포 · 기술 스택 (2026-08-24, 후속 대화)

위 여섯 항목을 다 정리한 뒤, 에이전트(나)가 "실제로 앱을 만드는 데 있어서 더 정해야
할 게 있는가"라는 질문에 스스로 짚은 것 중 하나가 배포였다 — 지금까지의 논의가 전부
"이미 켜져서 브라우저로 접속 가능한 상태"를 전제했는데, 그 앞단(사용자가 이 앱을 어떻게
설치·실행하는가)은 다룬 적이 없었다.

**확정 — 배포는 공개 git 저장소, 오픈소스.** 사용자 원문: "배포는 그냥 깃 레포
PUBLIC로, 오픈소스로 공개고." 별도의 설치 프로그램이나 패키징을 만들지 않는다. 이미
있던 원칙(`docs/vibe_coding_assistant_design.md` §14·15, `CLAUDE.md`의 대회 운영규정 —

아니라 그 원칙의 배포 형태로의 재확인이다.

**미정 — 기술 스택.** 사용자 원문: "스택은 리액트로 고민중. 이건 안 정했어." 참고할
점 하나: spike의 `apps/web`도 React + Vite로 만들어져 있어서, React를 고르면
"메커니즘만 가져간다"(`README.md` "상태" 절)는 원래 전제보다 더 많은 걸 — 코드 상당
부분까지 — 재사용할 수 있는 여지가 있다. 다만 이건 참고 사항이지 결정을 미는 것은
아니다. 확정되면 이 절을 갱신한다.

### 질문 7 — 아키텍처·기술부채 리뷰, 그리고 design.json 없는 진입 경로 (같은 날, 다른 세션의 구현을 이어서)

배포·스택을 정리한 뒤, 다른 세션(포트 5173에 별도로 띄운 것)이 질문 5의 결정을 그대로
spike에 구현했다는 것을 알게 되어 그 코드를 리뷰했다.

**리뷰 결과**: 범위(세 카테고리만 허용, 결합도·순환 의존 등은 명시적으로 금지)·격리
(`mode: "architecture"`, 읽기 전용)·해소 handoff(`renderArchitectureResolutionPrompt`가
bridge에서만 렌더되고 agent 입력 스키마엔 없음)·세션 정책(질문 4의 sitting 규칙대로
매번 새 세션)·저장(질문 5의 확정대로 JSON+MD 덮어쓰기)이 전부 문서와 정확히 일치했다.
실제 fixture로도 Codex가 세 카테고리를 각각 1건씩 정확히 제출한 것을 확인했다.

짚은 것 둘, 둘 다 조치함:

1. **회귀 검증 스크립트가 없었다.** Drift·Wiki와 달리 `npm run architecture`가 없어서
   재현 가능한 형태로 검증이 안 남아 있었다. `scripts/architecture-fixture.mjs` +
   `scripts/architecture.mjs`를 새로 만들어 해결했다 — 그 결과 "Claude는 아직 안
   돌려봤다"던 기존 한계도 이번에 실제로 확인됐다(두 provider 13/13).
2. **함수 시그니처 목록에 문자 수 캡이 없었다.** 개수 상한(1,000개)만 있어서 최악의
   경우 24만 자까지 갈 수 있었다 — 방금 정한 "토큰 비용은 항상 줄이는 방향으로"와
   어긋났다. `MAX_SIGNATURE_CHARS = 40,000`(Wiki와 같은 규모)을 추가했다.

**사용자가 화면 캡처를 보고 새로 짚은 것**: "관련 설계: REQ-1, REQ-2, REQ-3, ENT-1,
ENT-2, ENT-3"이 실제로 뭔지 묻다가 — "이게 지금 다른 프로젝트는 design.json이 없을
가능성이 높잖아"로 이어졌다. 확인해 보니 맞았다: `oversized-module`은 `designRefs`
(REQ/ENTITY)에 의존하는데, "이미 코드가 있는 프로젝트를 여는" 진입 경로는 애초에
인터뷰(그래서 design.json)를 거치지 않는다 — 이 카테고리가 가장 필요할 법한 경우에
근거가 통째로 사라지는 구조였다. 이 문제는 Drift도 이미 갖고 있다("기존 코드베이스에
DEC/RULE이 없을 때 무엇을 기준으로 할지 미정") — 다만 그때는 미정으로 남겨 뒀을 뿐
풀지 않았다.

사용자의 답 — 원문 그대로: "일단 우리 앱에서 만든 app_design.md가 있으면 그걸
활용하는 걸로 하고, 그와 비슷한 설계문서나 참고할 하네스가 없다면 방금 이야기한
b방향, '코드를 읽어보니 실제로 서로 다른 책임이 한 파일에 있다'고 판단하는 걸
허용하는 방향으로 가야할 것 같아."

**확정**: design.json이 있으면 그것으로 REQ/ENTITY 경계를 판단하고, 없으면 agent가
코드를 직접 읽어 책임 분리를 판단하는 것을 허용한다 — 그 경우 `designIds`는 비우고
근거는 코드 판단으로 직접 적는다. `duplicated-logic`·`stale-temporary-workaround`는
원래도 design에 의존하지 않으므로 영향이 없다. **Drift의 같은 문제는 이번에 풀지
않았다** — Drift는 "이 프로젝트가 정한 것 하나만 본다"는 원칙이 명시적 결정 자체에
의존하므로, 코드만 보고 대신 판단하는 fallback이 architecture와 같은 방식으로
성립하는지는 별도로 검토해야 한다.

**잡힌 회귀 — 프롬프트 길이가 저가 모델의 완결성을 해쳤다.** 이 규칙을 처음에는 8줄
문단으로 풀어 썼더니, Codex(`gpt-5.6-luna`, low)가 기존에 안정적으로 통과하던
with-design 시나리오에서 **2번 연속 `report_architecture`를 아예 안 부르고 turn을
끝냈다.** 3줄로 줄이자 다시 안정적으로 통과했다 — 약한 모델은 지시가 길어질수록
마지막 tool 호출까지 못 갈 수 있다는 것을 실측으로 확인했다. 프롬프트를 고칠 때
길이 자체를 회귀 위험으로 본다.

design.json 없는 변형(`withDesign: false`, `tmp/architecture-fixture-no-design`)을
검증 스크립트에 추가했고, 그 과정에서 `isSourceClean`의 버그(`git status --porcelain`
기본 옵션이 새로 생기는 `.project-intel/`을 한 줄로 뭉뚱그려 실제 내용을 못 봄)도
잡아 `--untracked-files=all`로 고쳤다.

```

```

`npm run typecheck`·`npm run build`·`npm run acceptance`(codex·claude 9/9, 회귀 없음)도

잠깐 재시작했다 — 재시작 후 child process 잔여 없이 깨끗하게 떠올랐다.

## 질문 8 — Drift의 "design.json 없는 진입 경로" 문제, 다시 보니 문제가 아니었다

질문 7에서 "Drift도 같은 문제(기존 코드베이스에 DEC/RULE이 없을 때 무엇을 기준으로
할지)를 갖고 있고 미정으로 남겨 뒀다"고 적어 뒀다. 첫 제품 구현(`app/`, Phase 4)에서
Drift를 실제로 붙이면서 이 질문을 다시 마주쳤다.

사용자의 질문 — 원문 그대로: "drift는 애초에 로컬에 커밋이 있는 상태에서 시작하는거
아니야?"

**확정**: 맞다. Drift는 Architecture와 달리 "기존 코드베이스를 여는" 진입 경로에서
애초에 제공되지 않는 것이 올바른 설계다. 이유는 Architecture와 근본적으로 다르다 —

- Architecture는 코드베이스 자체를 봐서 판단하는 기능이라, design.json이 없어도
  "코드를 읽고 직접 판단"하는 대체 경로가 성립한다(질문 7에서 이미 그렇게 고쳤다).
- Drift는 "이 프로젝트가 **정한 것**과 대조한다"는 것 자체가 존재 이유다. 대조할
  기준(DEC/RULE)이 없으면 무엇을 어겼는지 판단할 근거 자체가 없어서, Architecture
  방식의 fallback이 아예 성립하지 않는다.
- `resolveReviewStart()`의 시작점 결정 로직(마지막 리뷰 지점 → 없으면 **design.json이
  처음 커밋된 지점**부터) 자체가 "인터뷰 → design.json/harness 인계 → 그 위에 커밋이
  쌓인다"는 흐름을 전제로 만들어져 있다.

사용자가 덧붙인 것 — "하네스랑": 이 전제는 design.json 하나가 아니라 **인터뷰
인계 산출물 전체**(design.json + harness)다. Drift가 리뷰할 커밋들이 애초에 쌓이는
이유는 harness의 "## 커밋은 자주, 멈추지는 말고" 절이 사용자의 옆 agent에게 자주
커밋하라고 지시하기 때문이다(§6, `renderHarness`). 즉 design.json만 있고 harness가
없는 상태를 따로 가정할 필요가 없다 — `/api/design/export`가 둘을 항상 같이 내보내므로
Drift의 전제는 "design.json이 있다"가 아니라 "인터뷰 인계가 끝났다"로 보는 게 정확하다.

**결론**: Architecture처럼 design.json-optional fallback을 Drift에 만들 필요가 없다.
이걸로 질문 7 말미의 미해결 항목이 닫힌다.

**정정 — 실제 게이트는 design.json이 아니라 app_design.md 마커다.** 위 결론을 쓴
직후 사용자가 다시 짚었다: "일단 인터뷰를 통해 만들어진 건 json이 아니라
app_design.md이고 UX상에서 인터뷰에서 넘어온게 아니면 안쓰는 걸로 가자." 즉 "인터뷰
인계가 끝났다"를 판정할 때 봐야 할 파일은 사용자가 알아보는 `app_design.md`이지
`.project-intel/design.json`이 아니다 — 둘은 보통 같이 있지만, `/api/design/export`가
사용자가 이미 손으로 쓴 `app_design.md`는 덮어쓰지 않고 건너뛰면서도(§6 마커 규칙)
`.project-intel/design.json`은 그대로 쓰기 때문에, "design.json은 있지만 화면에 보이는
app_design.md는 사용자가 직접 쓴 것"인 상태가 생길 수 있다. 그 상태에서 design.json만
확인하면 실제로는 인터뷰가 인계되지 않은 프로젝트에서도 Drift가 동작해 버린다.

**구현**(`app/apps/bridge/src/index.ts`): `/api/review`가 `design.json`을 읽기 전에
`cameFromInterview(projectPath)`를 먼저 확인한다 — 프로젝트 루트의 `app_design.md`을
읽어 `HARNESS_MARKER`가 있는지만 본다. 없으면(파일이 없거나 사용자가 직접 쓴 것이면)
"인터뷰에서 넘어온 것이 아닙니다"로 거절하고, design.json 파싱 자체를 시도하지 않는다.
DEC/RULE 실제 값은 여전히 design.json에서 읽는다 — 이건 판정 기준(원본 데이터)이고,
app_design.md 마커는 그 기준을 쓸 자격이 있는 프로젝트인지 가리는 게이트라는 역할이
다르다.

## 질문 9 — Drift "피드백 받기": 재확인 루프의 종료 기준, 그리고 실제로 잡은 버그 둘

`app/`에서 Drift의 resolutionPrompt를 실제 옆 agent(Claude Code)에게 먹여 코드를 고치게
하는 것까지 시험해보다가, "고쳤는지 확인"하는 기능("피드백 받기")을 새로 만들게 됐다.
이 절은 그 기능의 UX 논의와, 만들면서 실제로 재현·수정한 버그 둘을 남긴다. 코드 변경
내역과 검증 로그의 원본은 `app/FINDINGS.md`에 있다 — 여기서는 제품 플로우 결정만 옮긴다.

### 루프 구조와 종료 기준

사용자가 지적 — 원문 그대로: "그리고 해당 drift 관리는 프롬프트주고 피드백주고 다시
프롬프트 주고 이 구조가 이어져야할 것 같은데, 이 구조가 언제 끝나는 지에 대한 기준을
정해야하지 않을까?"

에이전트(나)의 제안: finding 하나에 "피드백 받기" 버튼을 달아, 옆 agent가 고친 커밋
하나만 그 기준 하나에 대해 다시 확인한다. 아직 위반이면 지난 발견 + 이번 확인 결과를
합친 새 프롬프트를 다시 주고, 몇 번째 시도인지도 보여준다.

**확정** — 사용자 원문: "강제 종료 없이 갱신된 프롬프트 + 시도 횟수 표시로 가자.
그리고 적정 수준이 되면 해결이 완료되어야할 것 같아."

- 끝나는 조건은 하나뿐이다 — **agent 스스로 "해결됐다"고 판단하는 것**(`resolved:
  true`). 이 앱이 "N번 시도했으니 그만"이라고 임의로 끊지 않는다. "판단은 agent, 이
  앱은 보여주는 곳"이라는 §1.2·§3.5의 원칙을 재확인 루프에도 그대로 적용한 것이다.
- 몇 번째 시도인지는 화면에 계속 보여주되, 그 숫자를 근거로 앱이 뭔가를 강제하지는
  않는다 — 판단에 참고할 정보를 사용자에게 쥐여줄 뿐이다.
- 해결됐다고 확인되면 그 finding은 열린 목록에서 빠진다. 별도의 "완료" 상태를 계속
  붙들고 있을 필요가 없다.

### "그럼 전체 리뷰가 왜 필요한가"

사용자가 이어서 물었다 — 원문 그대로: "전체 리뷰가 drift 관리에서 필요한가?", 그리고
"지금 이 기능은 기능 확장 중에 생기는 drift를 관리하고 싶은거잖아. 그럼 전체 리뷰가
필요하냐는 얘기지. 기능 확장은 git diff에 다 남아있는데."

에이전트(나)가 두 갈래로 되물었다: (1) 기능 확장이 diff에 다 남으니 전체 리뷰가 당연히
있어야 한다는 뜻인지, (2) 기능 확장은 항상 diff 하나(또는 agent 세션 하나 분량의 커밋
묶음)로 딱 떨어지니 "지난 리뷰 이후 여러 커밋을 몰아 보는" 배치 개념 자체가 필요 없고
그냥 매번 직전 작업만 보면 되는 것 아니냐는 뜻인지.

사용자 답 — 원문: "2인데 직전 작업(커밋)이 하나는 아닐 가능성이 높짖" (직전 작업
단위가 여러 커밋일 수 있다는 지적).

**확정**: 전체 리뷰는 필요하다 — 다만 "여러 커밋을 몰아 보는 것"이 논점이 아니라,
**둘이 애초에 다른 질문에 답하기 때문이다.**

- **전체 리뷰** = "이 범위의 커밋들 중에 모르는 새 위반이 있나" (발견). finding이
  아직 없을 때 그것을 만들어내는 유일한 경로다.
- **피드백 받기** = "이미 아는 이 finding 하나가 고쳐졌나" (확인). 새 위반은 못 찾는다.

그리고 리뷰 범위(`resolveReviewStart`의 "지난 리뷰 이후 커밋들")는 이미 사용자가 말한
"직전 작업 단위"와 정확히 같은 것이라 바꿀 필요가 없었다 — 자주 확인하면 그 세션의
커밋 한두 개만, 뜸하게 확인하면 그 사이 여러 세션의 커밋이 한 번에 걸릴 뿐, 몇 개가
걸리든 같은 메커니즘이 그대로 맞다.

### 실제로 잡은 버그 1 — 안 고쳐진 finding이 다음 리뷰에서 조용히 사라짐

전체 리뷰는 "각 커밋을 자기 diff로만 판단한다"는, spike 때부터 있던 원칙(§3.3)을 그대로
따른다. 그런데 위반 커밋이 이미 리뷰돼 `lastReviewedSha`가 그 뒤로 넘어가면, 그 이후 어떤
새 커밋의 diff에도 옛 위반이 다시 나타나지 않으므로, 다음 리뷰가 findings 0건을 정직하게
보고하는 순간 화면에서 그 finding이 통째로 사라져 버렸다 — 실제로는 안 고쳐졌는데도.
"위반 등록 → 관련 없는 새 커밋으로 재리뷰(그래도 안 사라짐 확인) → 완전히 고치고
피드백 받기(그제서야 빠짐 확인)"까지 재현해서 검증했다.

**확정**: 화면에 보여줄 목록의 기준을 "이번 리뷰가 새로 찾은 것"에서 **"지금까지 나온
finding 중 아직 해결 확인이 안 된 것 전부"**로 바꾼다. `reviews.json`에 "피드백 받기가
해결됐다고 확인한 것"만 별도로 기록해서, 그 기록에 없는 과거 finding은 새 리뷰가 뭘
찾든 말든 계속 화면에 남는다. bridge가 재시작돼도 디스크 기록이라 사라지지 않는다.

### 실제로 잡은 버그 2 — "피드백 받기"가 부분 수정을 "해결됨"으로 잘못 판정

브라우저에서 실제로 나온 사례: 결제 모듈(`payment.js`)은 그대로 두고 그걸 부르는 곳
(`rental.js`)만 지운 부분 수정을, "피드백 받기"가 "위반 없음"으로 잘못 판정했다 — 같은
시나리오를 다른 세션에서는 여러 번 정확히 "아직 위반"으로 잡아냈던 것과 대조적이었다.

원인: 재확인 turn에는 파일을 읽을 도구가 없고, 주는 정보는 확인 대상 **커밋 하나의
diff뿐**이었다. 그 diff가 원래 지목된 파일 중 하나(`payment.js`)를 안 건드렸다면, agent는
"그 파일이 지금도 남아있는지"를 diff만으로는 확인할 방법이 없어 추론에 의존해야 했고,
이번엔 그 추론이 틀렸다.

**확정**: 재확인 turn에 diff만 주지 않는다. 원래 지목된 파일들의 **현재 실제 내용**
(삭제됐으면 그 사실 자체)을 diff와 함께 그대로 줘서, agent가 추론이 아니라 직접 읽고
확인하게 한다. 같은 조건(같은 모델·effort, 동일 부분 수정 시나리오)으로 재현한 뒤
재검증해서, 고친 뒤에는 "아직 위반 — payment.js가 남아있다"고 정확히 판정하는 것을
확인했다.
