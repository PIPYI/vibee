## 다음 대화를 이어갈 에이전트에게

이 문서는 단순 아이디어 메모가 아니라 **제품 플로우 논의를 이어가기 위한 인수인계 문서**다. 다음 에이전트는 먼저 이 문서 전체를 읽고 아래 원칙을 지킨다.

1. 아래에서 `확정`이라고 적은 내용을 다시 선택지로 되묻지 않는다.
2. 루트 `README.md`나 기존 설계 문서가 이 문서와 충돌하면, 기존 문구를 근거로 사용자의 결정을 되돌리지 않는다.
3. 기능들이 같은 프로젝트 디렉터리를 쓴다는 이유로 하나의 상태·세션·갱신 주기를 공유한다고 가정하지 않는다.
4. 아직 정하지 않은 지점은 한 번에 하나씩, 사용자 관점의 실제 동작으로 질문한다.
5. 시각화의 세부 표현보다 먼저 **비시각 기능들의 입력, 실행 시점, 결과 수명과 상호 격리**를 정한다.
6. 현재 spike의 화면과 코드는 검증 장치다. 제품 요구사항을 spike의 현재 구현에 맞춰 축소하지 않는다.

## 이 논의를 시작한 배경

사용자는 현재 프로토타입을 최종 앱으로 보지 않는다. 프로토타입은 Codex/Claude Code 연결, MCP 왕복, 인터뷰, Drift, Wiki 같은 메커니즘을 실제 에이전트로 검증하기 위한 것이다. 검증 결과는 활용하되, 사용자 입장에서 기능 경계와 상태 관리가 혼재되어 있어 **제품 앱은 새로 만드는 방향**을 전제로 한다.

논의의 출발점은 다음 우려였다.

> README에 적힌 기능들은 서로 다른 기능인데, 하나를 사용했을 때 다른 기능이나 프로젝트 데이터가 초기화되면 문제가 된다.

그 뒤 각 기능의 기준 시점과 입력을 하나씩 분리했다. 이 과정에서 기존 문서를 하나의 통합된 제품 플로우로 해석하는 오류가 여러 번 있었고, 사용자가 다음과 같이 바로잡았다.

- “다 별개의 기능이야.”
- “인터뷰는 사용자가 새로운 프로젝트를 시작하고 싶을 때 설계도를 만드는 기능이고, 설계도와 하네스를 만들고 나면 그걸로 그 기능은 끝.”
- “완전히 다른 앱을 만들고 싶다면 새 프로젝트를 생성하거나 다른 폴더를 선택하는 것.”
- “위키·코드 분석·아키텍처/기술부채 기능은 이미 있는 코드베이스를 연결했을 때가 기준.”
- Drift는 현재 프로젝트 전체 상태를 매번 다시 판단하는 것이 아니라 “커밋 기준”.
- 인계 이후 설계와 구현을 바꾸는 것은 “연결되어 있는 Codex나 Claude Code 앱의 역할”.
- Wiki는 “다 끝나고 채팅 분석해서 학습 목적”이며 커밋으로 코드가 바뀌는 것과 무관하다.
- 코드 분석·시각화는 필요할 때 새로 실행하면 된다.
- “다 끝난 상태”는 작은 작업 하나가 아니라 end-to-end로 하나의 결과물이 모두 만들어진 상태다.
- 우리 앱에는 프로젝트 디렉터리를 입력하는 칸이 있고, 앱과 에이전트는 같은 워크스페이스를 공유한다.
- 후속 기능을 실행하면 우리 앱에 연결된 에이전트가 그 기능에 필요한 코드를 읽는다. 기능에 따라 프로젝트 코드 전체가 필요할 수도 있고 세션의 채팅 기록이 필요할 수도 있다.

위 문장들이 이후 플로우 설계의 기준이다.

## 핵심 전제

- 루트 `README.md`에 적힌 기능들은 하나의 연속된 작업 단계가 아니라 **서로 다른 목적을 가진 별개 기능**이다.
- 프로젝트의 기본 단위는 사용자가 앱에 입력한 **프로젝트 디렉터리**다.
- 우리 앱과 연결된 Codex 또는 Claude Code는 같은 디렉터리를 워크스페이스로 사용한다.
- 같은 워크스페이스를 사용하더라도 기능별 입력, 실행 시점, 세션과 결과 수명은 서로 다를 수 있다.
- 한 기능을 실행했다고 다른 기능의 상태나 산출물을 초기화하거나 삭제하면 안 된다.
- 현재 프로토타입은 아키텍처와 구현 가능성을 검증한 spike다. 제품은 새로 만들고, 검증된 메커니즘만 가져간다.

### “별개 기능”의 정확한 뜻

별개 기능이라는 말은 기능끼리 어떤 데이터도 참고하지 못한다는 뜻이 아니다. 같은 프로젝트를 설명하므로 필요한 경우 설계도, 코드, 대화, Git 이력을 읽을 수 있다. 다만 다음은 분리한다.

- **사용 목적**: 설계, 학습, 코드 이해, Drift 검토, 구조/부채 파악은 서로 다른 사용자 목표다.
- **시작 조건**: 새 프로젝트에서만 쓰는 기능과 코드가 이미 있어야 쓰는 기능이 다르다.
- **주 입력**: 인터뷰 대화, 코딩 대화, 전체 코드, 커밋 diff 등 기능마다 다르다.
- **실행 주체와 권한**: 어떤 turn은 대화 전용이고, 어떤 turn은 코드 전체 읽기가 필요하다.
- **결과 수명**: 커밋마다 이어지는 결과와 사용자가 요청할 때 새로 만드는 결과가 다르다.
- **실패 및 초기화 범위**: 한 기능의 재실행·초기화·실패가 다른 기능의 데이터를 지우면 안 된다.

데이터 참조 가능성과 기능 수명주기 공유를 혼동하지 않는 것이 중요하다.

## 프로젝트 진입 경로

현재까지 두 가지 진입 경로가 확인됐다.

### 새 앱을 만드는 경우

```text
새 프로젝트 디렉터리 지정
→ 인터뷰
→ 설계도와 harness 인계
→ 같은 디렉터리에서 연결된 에이전트가 최초 결과물 전체 구현
→ 결과물이 end-to-end로 동작
→ 후속 기능을 필요에 따라 개별 실행
```

### 이미 코드가 있는 프로젝트를 여는 경우

```text
기존 프로젝트 디렉터리 지정
→ 인터뷰를 거치지 않음
→ 코드 분석·시각화 / 아키텍처·기술부채 등 필요한 기능 실행
→ 해당 기능이 요구하는 범위의 코드·기록을 연결된 에이전트가 읽음
```

기존 코드베이스 진입에서 Wiki가 동작하려면 분석할 수 있는 Codex/Claude Code 대화 기록이 실제로 있어야 한다. Drift는 DEC/RULE 같은 프로젝트 고유 기준이 없는 기존 저장소에서 무엇을 기준으로 할지 아직 정하지 않았다.

## 전체 사용자 흐름

```text
프로젝트 디렉터리 지정
        ↓
새 프로젝트라면 요구사항 인터뷰
        ↓
설계도 + 선택한 에이전트용 harness 생성
        ↓
같은 워크스페이스에서 Codex/Claude Code가 전체 앱 구현
        ↓
하나의 동작하는 결과물이 end-to-end로 완성됨
        ↓
사용자가 우리 앱에서 필요한 후속 기능을 개별 실행
        ↓
연결된 에이전트가 기능에 필요한 코드·대화·기록을 읽고 결과 생성
```

완성된 프로젝트를 우리 앱으로 다시 가져오거나 별도로 import하는 단계는 없다. 워크스페이스가 이미 공유되어 있으므로 사용자가 기능을 실행하면 그 시점에 연결된 에이전트가 필요한 자료를 읽는다.

### “다시 우리 앱으로 돌아온다”의 의미

기존 문서에는 “완성된 코드베이스가 다시 우리 앱으로 돌아온다”는 표현이 있다. 이것은 파일을 복사하거나 저장소를 재등록한다는 뜻으로 해석하면 안 된다.

- 프로젝트 경로는 이미 앱에 연결되어 있다.
- Codex/Claude Code와 우리 앱은 같은 디렉터리를 본다.
- 사용자는 구현이 끝난 뒤 우리 앱에서 원하는 기능을 누른다.
- 그 기능을 위해 시작된 agent turn이 현재 워크스페이스를 읽는다.
- 따라서 별도 import, re-link, 결과물 업로드 과정은 없다.

우리 앱이 외부 에이전트의 “완료”를 자동 감지해야 한다는 결정도 아직 없다. 현재 합의에서 중요한 것은 완료 이후 기능을 사용한다는 사용자 흐름이지, 자동 상태 판정이 아니다.

## 기능별 역할과 수명

### 요구사항 인터뷰

- 사용자가 **새로운 프로젝트를 시작할 때** 사용한다.
- 대화를 통해 설계도와 에이전트 harness를 만든다.
- 산출물을 인계하면 인터뷰 기능의 역할은 끝난다.
- 인계 후 인터뷰를 재개하여 설계를 수정하는 제품 경로는 두지 않는다.
- 이후 설계 변경과 실제 구현은 연결된 Codex 또는 Claude Code 앱의 역할이다.
- 완전히 다른 앱을 만들려면 새 프로젝트를 만들거나 다른 폴더를 선택한다.

#### 인터뷰가 읽고 쓰는 것

- 입력은 사용자가 만들고 싶은 앱에 대한 대화다.
- 시작 시점에는 코드가 없다는 전제다.
- 대화에서 ACTOR, REQ, SURFACE, ENTITY, FLOW, RULE, DEC 같은 설계 정보를 구조화할 수 있다.
- 출력은 사람용 설계 설명, `app_design.md`, 선택한 에이전트용 `AGENTS.md` 또는 `CLAUDE.md`, 이후 참조 가능한 구조화 원본이다.
- 인터뷰 turn은 소스 코드를 구현하거나 기존 프로젝트 문서를 무차별적으로 읽는 작업 turn이 아니다.

#### 인터뷰 종료 후

- 우리 앱 안에서 인터뷰 세션을 다시 열어 설계를 고치는 경로를 제품 플로우로 두지 않는다.
- 기존 설계 변경, 기능 확장, 코드 수정은 연결된 Codex/Claude Code 앱에서 사용자가 요청한다.
- 따라서 인터뷰의 대화 상태를 영구 복원해야 한다는 기존 spike의 미정 항목은 현재 제품 플로우의 우선 요구가 아니다.
- 단, 설계 원본을 Drift 기준이나 에이전트 컨텍스트로 보존하는 문제는 별개다. 인터뷰 UI를 재개하지 않는다고 DEC/RULE 원본까지 삭제하는 것은 아니다.

### 최초 end-to-end 구현

- 인계받은 에이전트는 설계의 일부 기능만 만드는 것이 아니라 **전체 결과물을 끝까지 구현**한다.
- 여기서 “완료”는 한 번의 작은 작업이나 커밋이 끝났다는 뜻이 아니다.
- 사용자가 처음 의도한 앱이 실제로 실행되는 하나의 결과물로 모두 만들어진 상태를 뜻한다.
- 이 완료 시점 이후에 프로젝트 확장과 학습 기능을 사용한다.

#### 앱과 코딩 에이전트의 역할 경계

- 실제 소스 코드 구현의 반복 루프는 Codex/Claude Code 앱에 있다.
- 우리 앱은 설계 산출물을 넘기고, 나중에 분석·학습·검토 기능을 실행한다.
- spike의 `mode: "task"`는 Browser → Agent 제어 채널이 실제 파일을 수정할 수 있는지 확인한 acceptance 장치다. 이를 제품의 내장 코딩 화면으로 확장하지 않는다.
- 우리 앱에서 Drift를 보고 수정이 필요하다고 판단하더라도 실제 수정은 연결된 코딩 에이전트가 맡는 방향이다. 우리 앱은 필요한 프롬프트와 컨텍스트를 넘길 수 있다.

### Wiki

- 최초 결과물이 완성된 뒤, 구현 과정에서 에이전트와 나눈 **채팅 기록을 분석하는 학습 기능**이다.
- 비전공자가 대화 중 접한 낯선 말을 “이 프로젝트에서는 무엇을 뜻하는지” 이해하게 한다.
- 필요하면 설명의 근거를 찾기 위해 현재 프로젝트 코드를 읽을 수 있다.
- 가치판단, 개선 권고, 위험 평가를 하지 않는다.
- 새 커밋이 생겼다는 이유로 위키를 초기화하거나 자동 갱신하지 않는다.
- Wiki의 입력은 커밋 이력이 아니라 학습 대상이 되는 에이전트 세션의 대화와 프로젝트 맥락이다.

#### Wiki 실행 해석

```text
최초 결과물 전체 완성
→ 사용자가 Wiki 기능 실행
→ 분석 대상 코딩 세션의 채팅 기록 읽기
→ 비전공자가 모를 만한 용어 후보를 agent가 판단
→ 사용자가 학습할 항목을 선택
→ 필요하면 agent가 프로젝트 코드에서 실제 사용 위치 확인
→ 이 프로젝트 기준의 설명 생성
```

- 단순 단어 빈도 추출은 검증에서 실패했다. 낯선 용어 후보 선정은 agent 판단이 필요하다.
- 코드는 용어가 이 프로젝트에서 실제로 무엇을 뜻하는지 근거를 대기 위해 읽는다.
- 일반적인 사전 설명만 만들지 않는다.
- “위험하다”, “바꿔야 한다”, “권장한다” 같은 평가는 배제한다.
- Wiki 결과를 Markdown과 구조화 원본으로 저장할 수 있다는 메커니즘은 검증됐지만, 최종 제품의 저장 위치와 수명은 아직 확정하지 않았다.
- 어느 코딩 세션을 대상으로 할지, 여러 세션을 합칠지, 확장 작업 후 새 Wiki 분석을 어떻게 시작할지는 아직 정하지 않았다.

### 코드 분석·시각화

- 이미 코드가 존재하는 완성된 코드베이스를 대상으로 한다.
- 사용자가 기능을 실행한 시점에 연결된 에이전트가 **프로젝트 코드 전체를 새로 읽고 분석**한다.
- 코드가 바뀌었다면 다음 실행에서 현재 코드를 다시 분석하면 된다.
- Wiki나 Drift의 상태를 입력으로 전제하거나, 이 기능 때문에 다른 결과를 초기화하지 않는다.

#### “코드 전체를 읽는다”의 의미

- 분석 범위는 일부 diff나 임의로 고른 파일이 아니라 프로젝트 전체다.
- 큰 저장소에서 agent가 한 prompt에 모든 원문을 넣어야 한다는 뜻은 아니다. 파일 탐색, 정적 분석 결과, Implementation Graph, 필요한 추가 조회 등으로 나누어 읽을 수 있다.
- 구현 최적화 때문에 사용자에게 알리지 않고 일부 폴더만 분석한 뒤 전체 프로젝트 결과인 것처럼 보여주면 안 된다.
- 이전 분석 결과를 증분 갱신하는 엔진을 내부 최적화로 쓸 수는 있지만, 사용자 플로우의 기준은 “기능을 실행한 현재 시점의 전체 프로젝트를 분석한 결과”다.
- 시각화의 Semantic Project Graph, Implementation Grounding, Framework Adapter 등 상세 설계는 `ontology/` 문서에 있다. 현재 대화에서는 시각 표현 자체보다 다른 기능과의 수명주기 분리가 우선이다.

### 설계 의도 ↔ 코드 Drift

- 인터뷰에서 저장한 DEC/RULE을 기준으로 이후 코드 변경을 검토한다.
- 검토 단위는 현재 코드베이스 전체 상태가 아니라 **개별 커밋과 그 커밋의 diff**다.
- 코드를 고치거나 확장하는 일은 연결된 Codex/Claude Code에서 수행한다.
- 커밋 변화에 따라 순차적으로 상태를 이어가는 기능은 현재로서는 Drift뿐이다.

#### 프로토타입에서 검증된 커밋 리뷰 메커니즘

다음은 현재 spike가 실제로 검증한 동작이며, 최종 UX는 별도로 정할 수 있다.

- 한 리뷰에서 여러 커밋을 처리하더라도 각 커밋은 **그 커밋 자신의 diff만으로** 판정한다.
- 이전에 본 커밋은 다시 판정하지 않도록 마지막 SHA를 저장한다.
- 위반 커밋과 무해 커밋을 함께 넣어 범용 코드 리뷰가 아니라 DEC/RULE 위반만 찾는지 검증했다.
- 코드를 고치면 새 커밋이 다음 검토 대상이 된다.
- 결정을 바꾸면 그 이후 커밋부터 새 기준을 적용한다는 메커니즘이 문서화돼 있다.

주의할 점:

- Drift는 버그, 스타일, 일반적인 베스트 프랙티스를 리뷰하는 기능이 아니다.
- 코드 분석·시각화가 전체 코드 스냅샷을 읽는 것과 Drift가 커밋 diff를 읽는 것은 서로 다른 입력 방식이다.
- 기존 코드베이스에 인터뷰 산출물이나 DEC/RULE이 없을 때 Drift를 제공할지, 제공한다면 기준을 어떻게 만들지는 미정이다.

### 아키텍처·기술부채

- 이미 코드가 존재하는 코드베이스를 연결했을 때 사용하는 별도 기능이다.
- 코드 구조와 필요한 프로젝트 기록을 어떤 범위로 읽을지, 결과를 일회성 분석으로 볼지 누적 이력으로 관리할지는 아직 확정하지 않았다.

현재 문서에는 의존성 증가, 결합도·응집도, 순환 의존성, 레이어 위반, 오래 남은 TODO, 과거 결정과의 비교가 후보로 적혀 있다. 그러나 이를 하나의 리포트로 묶을지, 사용자에게 어떤 질문에 답해주는 기능으로 만들지, Drift와 어디까지 분리할지는 다음 논의가 필요하다.

## 기능별 컨텍스트 원칙

기능마다 필요한 자료가 다르므로 모든 기능에 하나의 공통 세션이나 동일한 입력을 강제하지 않는다.

| 기능 | 주된 입력 |
| --- | --- |
| 인터뷰 | 새 프로젝트에 대한 사용자 대화 |
| Wiki | 완성 과정의 에이전트 채팅 기록 + 설명에 필요한 프로젝트 코드 |
| 코드 분석·시각화 | 실행 시점의 프로젝트 코드 전체 |
| Drift | DEC/RULE + 아직 검토하지 않은 커밋 diff |
| 아키텍처·기술부채 | 기존 코드베이스 + 범위가 확정될 프로젝트 기록 |

따라서 기능을 실행할 때 해당 기능 전용으로 필요한 세션, 읽기 권한과 컨텍스트를 구성해야 한다. 프로젝트 디렉터리를 공유한다는 사실은 모든 기능이 같은 대화 기록이나 상태를 공유한다는 뜻이 아니다.

### 기능 실행 시 agent 컨텍스트에 대한 현재 합의

- 앱의 프로젝트 경로가 agent의 `cwd`가 된다.
- 사용자가 기능 버튼을 누르면 우리 앱이 연결된 agent를 실행할 수 있다.
- agent는 기능에 맞는 읽기 범위를 가져야 한다.
- Wiki는 세션 대화와 코드 근거가 필요하다.
- 코드 분석·시각화는 전체 프로젝트 의미를 파악해야 한다.
- Drift는 DEC/RULE과 커밋 diff가 핵심이다.
- 인터뷰는 새 앱에 관한 사용자 대화가 핵심이고 코드 구현 도구는 필요 없다.

기능별로 별도 mode나 세션 키를 사용하는 spike의 격리 메커니즘은 참고할 수 있다. 다만 최종 제품에서 “항상 새 세션”, “항상 기존 세션” 중 하나를 모든 기능에 공통 적용하면 안 된다. 특히 Wiki는 기존 코딩 대화를 읽어야 하므로 새 빈 세션만으로는 입력을 얻을 수 없다.

## 검증된 기술 기반과 제품에 가져갈 것

현재 spike에서 다음은 실제 Codex와 Claude Code 양쪽으로 검증됐다.

- Browser/App이 Agent Adapter를 통해 로컬 agent turn을 시작할 수 있다.
- agent의 작업 디렉터리를 사용자가 지정한 프로젝트 경로로 설정할 수 있다.
- 진행 이벤트를 provider 중립 `AgentEvent`로 정규화해 WebSocket으로 앱에 보낼 수 있다.
- agent가 MCP로 앱 컨텍스트를 읽고 구조화된 결과를 다시 앱에 보낼 수 있다.
- Codex와 Claude의 raw 프로토콜 차이를 Bridge/Adapter 안에 가둘 수 있다.
- 인터뷰, 읽기 전용 리뷰, 읽기 가능한 Wiki turn을 서로 다른 권한과 문서 로딩 정책으로 격리할 수 있다.
- 인터뷰에서 구조화된 설계 원본을 만들고 사람용 문서와 harness를 결정적으로 렌더할 수 있다.
- DEC/RULE 기반 커밋 Drift 판정과 대화 기반 Wiki 용어 추출이 실제 agent에서 동작했다.

제품에 유지할 아키텍처 경계:

```text
App → Agent Adapter → Codex/Claude Code     실행 채널
Agent → MCP → Core/Project Store            컨텍스트·도구 채널
Agent/Bridge → Event Stream → App           진행·결과 채널
```

MCP를 Agent 실행 API처럼 사용하지 않고, App이 파일을 직접 수정하는 코딩 도구가 되지 않는다는 원칙도 유지한다.

## 더 이상 전제로 삼지 않는 초기 구상

- 인계 후 우리 앱에서 인터뷰를 이어서 설계를 다시 내보내는 흐름
- 인터뷰와 Drift를 하나의 기능 수명주기로 보는 구조
- 모든 기능을 하나의 end-to-end cycle로 묶는 구조
- 완성된 프로젝트를 우리 앱에 다시 import하거나 연결하는 별도 단계
- 모든 분석 결과를 커밋 변경에 맞춰 함께 무효화하거나 자동 갱신하는 구조
- Wiki를 코드 변경 감시나 의사결정 평가 기능으로 보는 설명

추가로 다음 질문도 이미 답이 나왔으므로 반복하지 않는다.

- “완성된 프로젝트를 어떤 방식으로 다시 import할 것인가?” → import하지 않는다. 같은 워크스페이스다.
- “커밋이 바뀌면 Wiki·코드 분석·아키텍처 결과를 모두 어떻게 무효화할 것인가?” → 공통 무효화 전제가 잘못됐다.
- “인계 후 설계를 우리 앱의 인터뷰에서 다시 고칠 것인가?” → 아니다. 연결된 코딩 에이전트가 담당한다.
- “Wiki는 작업 하나가 끝날 때마다 실행하는가?” → 작은 작업 완료가 기준이 아니다. 최초 end-to-end 결과물 전체가 완성된 이후가 출발점이다.
- “코드 분석은 이전 결과를 계속 유지·동기화하는가?” → 사용자가 기능을 실행할 때 현재 전체 코드를 새로 분석하는 것이 사용자 기준이다.

## 아직 정하지 않은 것

- 프로젝트 디렉터리를 지정한 직후 보여줄 첫 화면과 기능 진입 방식
- 기능별 세션을 새로 만들지, 기존 에이전트 세션 중 무엇을 선택할지에 대한 규칙
- 여러 코딩 세션 가운데 Wiki가 분석할 대화를 정하는 방식
- 아키텍처·기술부채 분석의 정확한 입력, 결과 형식과 이력 수명
- 각 기능의 결과를 앱과 `.project-intel/` 중 어디에 어떤 형태로 저장할지
- 기능 실행 전 코드 전체를 읽는 방식과 큰 프로젝트에서의 컨텍스트 분할 전략

## 다음 대화의 권장 시작점

다음 에이전트는 프로젝트 첫 화면을 추상적으로 다시 묻기보다, **기능별 실행 버튼을 눌렀을 때 어떤 자료와 어떤 agent session을 선택해야 하는지**부터 좁히는 것이 좋다.

가장 가까운 미정 지점은 Wiki다. Wiki는 전체 결과물이 완성된 뒤 코딩 채팅을 분석하지만 실제 프로젝트에는 다음이 있을 수 있다.

- 인터뷰 세션
- 최초 전체 구현 세션
- 중간에 새로 시작한 여러 코딩 세션
