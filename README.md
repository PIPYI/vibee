# Vibee 🐝

<img width="200" height="200" alt="vibee-logo" src="https://github.com/user-attachments/assets/220ffd02-fccf-4a1f-a0a8-1fd4c819c105" />


> 비전공자가 AI에게 코드를 맡기는 데서 그치지 않고, **무엇을 만들지 먼저 설계하고 자신이 만든 결과물을 이해하며 AI를 주도적으로 활용하도록 돕는 바이브코딩 보조 도구**

Vibee는 Codex 또는 Claude Code 같은 로컬 Coding Agent를 프로젝트 지식 계층과 연결하는 연동 앱입니다. 새로운 코딩 AI를 만드는 대신, 사용자가 이미 쓰고 있는 Coding Agent가 더 명확한 설계와 프로젝트 맥락을 바탕으로 작업하도록 돕고, 구현 후에는 설계 이탈·코드 구조·개발 과정의 개념을 사용자가 이해할 수 있는 형태로 보여줍니다.

브라우저 화면, 로컬 Bridge, Coding Agent가 같은 프로젝트 디렉터리를 공유하며 동작합니다. Vibee 자체는 별도의 클라우드 백엔드나 회원 계정, 모델 API Key를 요구하지 않습니다.

## 프로젝트 소개

생성형 AI를 이용하면 프로그래밍 경험이 부족해도 자연어만으로 앱을 만들 수 있습니다. 그러나 요구사항과 구조를 충분히 정리하지 않은 채 “~해줘”라는 짧은 요청으로 구현을 시작하면 기능이 즉흥적으로 추가되고, 사용자는 자신이 만든 프로그램의 구조와 동작을 이해하지 못한 채 결과물에만 의존하기 쉽습니다.

Vibee는 이 문제를 다음 두 방향에서 해결합니다.

1. **구현 전에는 생각을 구조화합니다.** 대화형 인터뷰로 아이디어를 구체화하고, 사람과 Coding Agent가 함께 참고할 수 있는 설계도와 프로젝트 지침을 만듭니다.
2. **구현 후에는 결과물을 이해하고 관리하게 합니다.** 실제 코딩 대화와 프로젝트 코드를 바탕으로 개인 Wiki, 설계 이탈 검토, 구조 점검, 시스템 구조 시각화를 제공합니다.

Vibee의 목표는 AI가 더 많은 코드를 대신 작성하게 하는 것이 아니라, 비전공자가 자신의 의도를 잃지 않고 AI와 협업하며 개발 과정에서 지식과 프로젝트 주도권을 함께 쌓도록 돕는 것입니다.

## 주요 대상

- 자연어로 처음 앱을 만들어보는 비전공자와 초보 개발자
- AI로 프로토타입을 만드는 기획자, 디자이너, 학생, 메이커
- 기능을 계속 추가하다가 프로젝트의 최초 의도나 구조를 놓치기 쉬운 사용자
- 자신이 만든 프로젝트나 참고할 코드베이스의 전체 구조를 빠르게 이해하고 싶은 사용자

## 핵심 특징과 차별점

### 기존 Coding Agent를 더 잘 활용하는 BYOA 구조

Vibee는 자체 모델 API로 코드를 생성하는 또 하나의 Coding Agent가 아닙니다. 사용자가 이미 설치하고 로그인한 Codex CLI 또는 Claude Code를 연결하는 **BYOA(Bring Your Own Agent)** 방식입니다. 모델 선택과 실제 소스 코드 작성은 Coding Agent가 담당하고, Vibee는 설계·학습·분석·검토에 필요한 맥락과 화면을 제공합니다.

### 프로젝트 전 과정을 잇는 지식 계층

Vibee는 한 번의 프롬프트를 잘 작성하는 데서 끝나지 않습니다. 처음 정한 설계, 실제 구현 과정의 대화, 현재 코드, Git 커밋을 기능별로 필요한 범위만 읽어 다음 질문에 답합니다.

| 사용자의 질문 | Vibee 기능 | 주된 입력 |
| --- | --- | --- |
| 무엇을 만들어야 할까? | 설계하기 | 새 프로젝트에 대한 사용자 대화 |
| 처음 정한 방향에서 벗어났을까? | 설계이탈관리(Drift) | 설계의 DEC/RULE + 아직 검토하지 않은 커밋 diff |
| 기능을 붙이는 동안 구조가 나빠졌을까? | 구조개선 | 현재 코드 구조 + 필요한 설계 정보와 Git 이력 |
| 구현 중 그냥 지나친 용어는 무엇일까? | 위키 | 실제 Coding Agent 세션 대화 + 설명에 필요한 프로젝트 코드 |
| 이 프로젝트는 어떻게 동작할까? | 구조파악 | 실행 시점의 프로젝트 코드 전체 |

각 기능은 같은 프로젝트를 보지만 목적, 입력, 실행 시점과 결과 수명이 서로 독립적입니다. 한 기능을 실행해도 다른 기능의 대화나 결과가 초기화되지 않습니다.

### 판단은 Agent가, 사실 수집은 코드가

파일 크기, 함수 위치, TODO의 생성 시점, 커밋 diff처럼 프로그램이 정확히 계산할 수 있는 정보는 먼저 정리하고, “서로 다른 코드가 실제로 같은 역할을 하는가?”처럼 의미 판단이 필요한 부분만 Agent에 맡깁니다. 이를 통해 불필요한 컨텍스트와 토큰 사용을 줄이면서 판단 근거를 분명하게 유지합니다.

### 분석과 수정을 분리

Vibee는 프로젝트를 이해하고 판단할 수 있는 자료를 보여주는 곳입니다. Drift나 구조개선에서 문제가 발견되어도 Vibee가 소스 코드를 직접 고치지 않습니다. 대신 근거와 수정용 프롬프트를 제공하고, 실제 변경은 사용자가 선택한 Codex 또는 Claude Code에서 수행합니다.

## 주요 기능

### 1. 설계하기 — 아이디어를 구현 가능한 설계도로

새 프로젝트를 시작할 때 대화형 인터뷰를 진행합니다. 단순한 자유 입력만 받는 대신 질문의 이유, 예시 답변, 진행 상태를 함께 보여주어 비전공자도 자신의 생각을 단계적으로 구체화할 수 있습니다.

인터뷰는 사용자, 요구사항, 화면, 저장 데이터, 주요 흐름, 규칙, 설계 결정 등을 `ACTOR`, `REQ`, `SURFACE`, `ENTITY`, `FLOW`, `RULE`, `DEC` 형태로 구조화합니다. 사용자는 생성된 초안을 읽고 자연어로 정정할 수 있으며, 인터뷰가 끝나면 다음 산출물을 만듭니다.

- 사람이 읽는 프로젝트 설계 설명과 `app_design.md`
- 이후 기능이 참조할 수 있는 구조화된 설계 원본 `design.json`
- 선택한 Agent가 지속적으로 읽는 `AGENTS.md` 또는 `CLAUDE.md`

산출물은 Coding Agent와 공유하는 프로젝트 디렉터리에 저장됩니다. 이후 Agent는 이 설계와 지침을 바탕으로 전체 앱을 구현하며, 추가 설계 변경과 소스 코드 수정도 해당 Agent에서 이어갑니다. Vibee의 인터뷰는 설계 인계가 끝나면 역할을 마칩니다.

### 2. 설계이탈관리(Drift) — 최초 결정과 이후 변경을 비교

기능을 계속 확장하다 보면 각각의 수정은 자연스러워 보여도, 결과적으로 처음 정한 중요한 규칙이나 결정에서 벗어날 수 있습니다. Drift는 인터뷰에서 정한 `DEC`와 `RULE`을 기준으로 **아직 검토하지 않은 각 Git 커밋의 diff**를 확인합니다.

이 기능은 버그, 코드 스타일, 일반적인 베스트 프랙티스를 평가하는 코드 리뷰가 아닙니다. 오직 “이 변경이 이 프로젝트에서 명시적으로 정한 설계 의도를 어겼는가?”에 집중합니다.

- 마지막 검토 지점 이후의 커밋을 각각 자신의 diff 기준으로 판정합니다.
- 발견된 이탈은 근거와 함께 열린 항목으로 유지합니다.
- 수정을 위한 프롬프트를 생성해 연결된 Coding Agent에 전달할 수 있습니다.
- 수정 후 **피드백 받기**로 해당 커밋과 기준만 다시 확인합니다.
- 문제가 남아 있으면 이전 발견과 새 확인 결과를 합친 갱신 프롬프트와 시도 횟수를 보여주며, Agent가 해결됐다고 판단할 때까지 반복할 수 있습니다.

Drift는 Vibee의 설계 인터뷰와 인계 과정을 거쳐 비교 기준이 존재하는 프로젝트에서 사용합니다.

### 3. 구조개선 — 누적된 구조 문제와 기술부채 점검

기능을 빠르게 덧붙이는 과정에서 비전공자가 직접 발견하기 어려운 구조적 문제를 현재 코드 전체에서 점검합니다. 범용 정적 분석을 모두 제공하기보다 바이브코딩에서 반복적으로 나타나는 세 가지 증상에 집중합니다.

1. **파일·모듈 비대화** — 하나의 파일에 서로 다른 책임이 지나치게 모였는지 확인합니다. 설계 자료가 있으면 `REQ`와 `ENTITY` 경계를 참고하고, 없으면 실제 코드를 읽어 책임 분리를 판단합니다.
2. **의미가 같은 로직의 중복** — 단순 복사·붙여넣기가 아니라 표현은 달라도 같은 일을 하는 함수가 여러 곳에 생겼는지 찾습니다.
3. **방치된 임시 조치** — `TODO`, 임시 구현 등의 표시가 생긴 뒤 그 위에 변경이 계속 쌓여 되돌리기 비용이 커졌는지 확인합니다.

구조개선은 실행할 때마다 현재 프로젝트 상태를 새로 살펴보고, 발견 항목의 근거·심각도·다음 행동을 제시합니다. 실제 리팩터링은 Vibee가 수행하지 않으며, 복사 가능한 리팩터링 프롬프트를 연결된 Coding Agent에 전달합니다.

### 4. 위키 — 실제 코딩 대화를 나만의 학습 자료로

위키는 **설계 인터뷰에서 나온 용어를 설명하는 기능이 아닙니다.** 프로젝트를 구현하면서 Codex 또는 Claude Code와 실제로 나눈 코딩 세션 대화를 분석하는 학습 기능입니다.

개발 중에는 결과물을 만드는 데 집중하느라 모르는 용어가 나와도 질문을 미루거나 그냥 지나치기 쉽습니다. Vibee는 프로젝트 완성 후 해당 프로젝트의 코딩 대화에서 비전공자에게 낯설 수 있는 개발·AI 용어를 Agent의 판단으로 추출합니다. 사용자가 용어를 선택하면 필요할 때 현재 코드를 확인하여 다음 내용을 설명합니다.

- 용어의 짧은 정의
- 일반론이 아닌 **이 프로젝트에서의 실제 의미와 역할**
- 관련 파일·함수·코드 위치 등 설명의 근거
- 함께 알아두면 좋은 관련 용어

생성한 페이지는 미리보기로 확인한 뒤 **내 위키**에 추가할 수 있습니다. 이미 만든 설명은 다시 Agent를 호출하지 않고 재사용하며, 프로젝트를 다시 열어도 저장된 학습 내용을 확인할 수 있습니다. 즉, 사용자가 직접 만든 프로젝트가 곧 개인화된 프로그래밍 교재가 됩니다.

### 5. 구조파악 — 긴 설명 대신 한눈에 보는 시스템 지도

직접 만든 프로젝트나 참고할 기존 프로젝트의 구조를 파악할 때, AI의 긴 줄글 설명이나 문자 기반 구조도만으로는 전체 흐름을 이해하기 어렵습니다. 구조파악은 실행 시점의 프로젝트 코드 전체를 분석해 현재 동작하는 시스템의 런타임 아키텍처를 SVG 다이어그램으로 표현합니다.

일부 파일이나 최근 diff만 보고 전체를 추정하지 않으며, 구성 요소와 연결 관계를 실제 구현에 근거해 보여주는 것을 목표로 합니다. 코드가 변경되면 기능을 다시 실행해 현재 상태를 새로 분석할 수 있고, Wiki·Drift·구조개선의 상태와는 독립적으로 동작합니다.

## 사용 흐름

### 새 앱을 만드는 경우

```text
새 프로젝트 디렉터리 지정
→ 설계 인터뷰로 아이디어와 요구사항 구체화
→ app_design.md + design.json + AGENTS.md/CLAUDE.md 생성
→ 같은 디렉터리에서 Codex/Claude Code가 전체 앱 구현
→ 완성 후 필요한 기능을 개별 실행
   ├─ 위키로 개발 중 등장한 개념 학습
   ├─ Drift로 이후 커밋의 설계 이탈 확인
   ├─ 구조개선으로 누적된 구조 문제 점검
   └─ 구조파악으로 현재 시스템 시각화
```

### 이미 코드가 있는 프로젝트를 여는 경우

```text
기존 프로젝트 디렉터리 지정
→ 별도의 업로드나 재가져오기 없이 같은 워크스페이스 연결
→ 구조개선·구조파악 등 필요한 기능 실행
→ Coding Agent가 각 기능에 필요한 범위의 코드와 기록을 읽어 결과 생성
```

위키를 사용하려면 해당 프로젝트에서 선택한 Coding Agent의 실제 세션 대화가 있어야 합니다. Drift는 Vibee의 인터뷰로 만든 설계 기준이 있어야 하므로 일반 기존 코드베이스에는 제공되지 않습니다.

## 동작 방식과 아키텍처

```text
사용자
  │
  ▼
Vibee Web (React)
  │  기능 실행 요청 / 결과 표시
  ▼
Local Bridge
  ├─ Agent Adapter ───────────────▶ Codex CLI / Claude Code
  ├─ WebSocket Event Stream ─────▶ 진행 상태와 결과를 Web에 전달
  └─ Project Store ◀──── MCP ───── Coding Agent가 컨텍스트를 읽고 구조화된 결과를 반환
                                      │
                                      ▼
                            Shared Project Workspace
```

Vibee는 역할이 다른 세 통신 경로를 분리합니다.

| 경로 | 역할 |
| --- | --- |
| Agent Control | Web의 요청을 Local Bridge와 Agent Adapter를 통해 Codex 또는 Claude Code 작업으로 시작합니다. |
| Event Stream | 서로 다른 Agent의 진행 이벤트를 공통 형식으로 정규화하고 WebSocket으로 실시간 전달합니다. |
| MCP Tool | Agent가 앱의 설계·검토 컨텍스트를 읽고, 자유 텍스트 대신 구조화된 판단 결과를 Vibee에 돌려줍니다. |

`Agent Adapter`는 Codex와 Claude Code의 서로 다른 실행·세션 프로토콜을 감추므로 Web과 Bridge의 상위 기능은 동일한 방식으로 두 Agent를 다룰 수 있습니다. 각 기능은 필요한 권한과 컨텍스트가 다르므로 인터뷰, Wiki, Drift, 구조개선 등의 실행 상태를 분리합니다.

## BYOA와 로컬 실행

- **사용자 소유 Agent 사용** — 이미 설치하고 인증한 Codex CLI 또는 Claude Code를 사용합니다.
- **API Key 입력 불필요** — Vibee가 OpenAI·Anthropic API를 직접 호출하거나 사용자의 인증 정보를 복사하지 않습니다.
- **로컬 중심 구성** — Web, Bridge, MCP 서버와 프로젝트 데이터는 사용자 컴퓨터에서 실행·저장됩니다.
- **공유 워크스페이스** — Vibee와 Coding Agent가 같은 프로젝트 디렉터리를 보므로 별도의 업로드, import, 동기화 단계가 없습니다.
- **Provider 독립 UI** — Agent별 프로토콜 차이는 Adapter 내부에서 처리하고, 화면에는 공통된 진행 상태와 결과를 표시합니다.
- **소스 코드 수정 권한 분리** — Vibee는 설계·분석 산출물과 Agent용 지침을 관리하며, 실제 애플리케이션 코드는 연결된 Coding Agent에서 수정합니다.

> Vibee 구성 요소와 프로젝트 데이터 관리는 로컬에서 이루어지지만, Codex 또는 Claude Code 자체의 모델 통신 방식과 데이터 처리는 각 서비스의 설정 및 정책을 따릅니다.

## 시작하기

설치부터 실행까지 자세한 안내는 [`startup.md`](./startup.md)를 참고하세요. 요약하면:

```bash
npm install
npm run build
npm run bridge   # 터미널 1
npm run web      # 터미널 2
```

Codex를 쓴다면 최초 한 번 `npm run mcp:register`로 MCP 서버를 등록해야 합니다.
Claude Code는 별도 등록이 필요 없습니다.

## 구조

- `apps/bridge` — HTTP API + WebSocket + Coding Agent adapter를 갖는 로컬 서버
- `apps/web` — 브라우저 화면 (React)
- `packages/mcp-server` — Coding Agent가 앱에 도달하는 MCP tool을 노출하는 stdio 서버
- `packages/protocol` — 위 세 층이 공유하는 타입
- `packages/system-map` — "구조파악" 기능의 검증·레이아웃·SVG 렌더링 로직
